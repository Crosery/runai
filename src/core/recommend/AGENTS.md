# core::recommend — LLM skill router

## Purpose
Opt-in skill auto-routing. A small LLM (default `deepseek-v4-flash` via OpenAI-compatible API) looks at the user prompt + the list of installed skills (name + AI summary + tags) and returns the top-K most relevant skills plus a one-sentence `reasoning:` line. The `UserPromptSubmit` hook injects this as candidate list + activation command into the main Claude Code prompt; the main agent then runs `runai-client activate <name>` to print the cached or freshly-fetched `SKILL.md`. `runai-client activate` is the agent-facing source of truth for "skill adopted": it calls `/skills/use/{name}` or writes a durable local outbox event before printing content.

Disabled by default. User must run `runai recommend setup` (interactive) or write `~/.runai/config.toml` manually before any LLM call happens.

### Submodule invariants (load-bearing — do not break silently)
- **`enrich.rs` worker pool** uses `std::thread::scope` with per-worker `Arc::clone` (queue / report_mu / progress / cfg / api_key / db_path) and each worker opens its **own** `rusqlite` `Database::open(&db_path)` — the `Connection` is `!Sync`, so the per-worker open is mandatory, not incidental. Never consolidate to one shared connection.
- **`lang_validation.rs` is moved verbatim.** The script-aware CJK/kana/hangul counters + the `task`-anchor rule (`field_matches_lang(.., is_anchor=true)`) are what make a whole-English summary structurally impossible to pass a `zh` index. Aggregate ratios are wrong on both ends — do not "simplify".
- **Prompt templates flow through the centralised registry `crate::core::prompts`** (PLANNING §1.3). Each submodule reads `crate::core::prompts::PROMPT_<NAME>` instead of its own `include_str!`, then calls `crate::core::prompts::template_body(...)` before sending text to an LLM or hook stdout. The raw `.md` files keep a first-line `<!-- prompt: ... -->` metadata comment for grep/doc use; runtime output strips it. Edit `src/core/prompts/*.md` to retune wording; see `src/core/prompts/AGENTS.md` for the per-prompt caller / variable / output contract.
- **Per-user prompt-injection toggles are resolved inside `router::recommend_for_user`** by reading the requesting `user_id`'s `UserPrefs::prompt_injection_flags` exactly once per request. `inject_history` / `inject_cwd` / `inject_project_context` short-circuit the matching block to the empty string when off; the default (missing key) is on. (`recommend_already_routed` was retired with session no-repeat — see below.) Unauthenticated requests (`user_id = None`) use `UserPrefs::default()` so they never read another tenant's prefs. The router does NOT cache prefs across requests — switching the logged-in api_key is reflected on the next call. Local hooks must arrive with a valid `$HOME/.runai-identity` or HTTP Bearer to hit this path; stale credentials return empty hook output instead of falling back to anonymous defaults. Covered by `tests/prompts_multiuser_e2e.rs` and `tests/user_prefs_e2e.rs`.
- **Recommend routing is explicitly two-stage.** Stage 1 calls the same configured recommend model with `recommend_intent.md` to compress the raw user turn + prior compact session memory into a short BM25 intent artifact. Stage 2 runs BM25/candidate gating from that artifact, then calls the router LLM with `recommend_user.md` over the retrieved candidates. The dashboard stores both waves: `intent_llm_input` / `intent_llm_output` / `intent_status` / `intent_error_msg` / `bm25_candidates_json`, then the existing `llm_input` / `llm_raw_response` / `hook_output`.
- **Each stage has a FIXED system prompt and a lean, dynamic user message (prefix-cache design).** Stage 1's system message is the whole of `recommend_intent.md` (no placeholders, byte-identical every request → provider prefix cache hits it); its user message (`build_intent_user_message`) carries ONLY dynamic fields, each exactly once — `cwd:` line, `agent_cli:` line, `session_memory:` block, then the current prompt under `当前用户输入：`, truncated to `LLM_PROMPT_CHAR_CAP` (2000) chars. The deterministic intent (`build_intent_summary`) is NOT sent to the model — it is the code-side fallback used only when the Stage-1 call errors. This killed the previous double injection (whole template sent as system AND as a filled user message, plus the deterministic fallback re-embedding memory/cwd/prompt a second time). Stage 2's system message is all of `recommend_system.md`; its user message (`recommend_user.md`) carries the current prompt exactly once (truncated), the intent summary, the candidate listing, and the optional cwd/history/project-context blocks. Both LLM calls set `temperature = 0` and a bounded `max_tokens` (`INTENT_MAX_TOKENS = 512`, `ROUTER_MAX_TOKENS = 400`); enrich passes `max_tokens = None` for the full budget. Regression: `tests/recommend_prompt_arch_e2e.rs` records the outgoing HTTP bodies and asserts the two system messages are byte-identical across requests, the Stage-1 user fields appear exactly once, and the message/hook sizes stay under a fixed ceiling.
- **Session no-repeat suppression was removed (每轮独立全质量推荐).** The router no longer reads `router_session_recommended_skills` to inject an `ALREADY_ROUTED` block into the Stage-2 user message or a "已推参考池" recall block into the hook output; the same skill may be recommended on consecutive turns and every round is a full-quality recommend. `router_session_recommended_skills` stays available as pure telemetry but never enters any prompt. `record_session_adoption` (activation-time adoption for the feedback radar) is unaffected. This also removed two per-request DB round-trips. `recommend_already_routed.md` was deleted; `hook_output.md` dropped its `{SESSION_HISTORY_BLOCK}` and `{SKIP_REMINDER_BLOCK}`. `format_for_hook_full`'s `session_history` and `skip_reminder` params are retained for signature compatibility but ignored by the renderer.
- **Transcript history is tightly bounded.** The Stage-2 history block threads at most `HISTORY_TURN_LIMIT` (4) recent turns, each capped at `TRANSCRIPT_MSG_CHAR_CAP` (250) chars with a `…` truncation marker — enough to tell whether the current prompt replies to the prior recommendation, without dumping long assistant messages.
- **Intent recognition happens before BM25 and starts from a compact true-intent line.** `intent::recognize_intent(current_prompt, previous_session_memory, cwd, client_kind)` remains the deterministic fallback and classifier; it first extracts the tail/current request from long pasted context, then produces a compact summary plus `domain_tags`, `include_terms`, `exclude_terms`, and `ScenarioConstraint`s. Deterministic gates distinguish ordinary Android emulator debugging from KTV/车机/WebView/H5 debugging, image regeneration with reference-image constraints, and prompt/router/BM25 audit from general repository architecture work. This gate runs before the LLM sees candidates, so wrong-domain skills are removed from the candidate listing rather than relying on prompt wording alone.
- **Current-session intent memory is bounded, scoped, one-turn delayed, and compact-only.** When `UserPrefs.intent_memory_enabled` is true, each recommend call stores the Stage-1 `intent_llm_output` under `(session_id, user_id, client_kind)` in `router_intent_memory`, then trims to `intent_memory_limit` by dropping the oldest rows. Default limit is 10; `0` disables storage/injection. The router reads the existing queue before Stage 1, and appends the current compact intent only after Stage 1 finishes; raw user prompts never enter this queue. Historical sessions are not backfilled into the prompt.
- **Candidate gating is relevance-first.** `router::candidate_allowed_by_intent` applies structured-intent constraints before BM25/rerank. In ordinary Android emulator debugging, KTV/车机/WebView/H5 specialized candidates are filtered unless the user actually mentioned that domain; generic Android/ADB/emulator skills remain eligible even if they share a broad group. In image regeneration/reference-image follow-ups, only image generation/editing candidates reach the router LLM, and `not-for` text is never treated as positive BM25 evidence. `llm_score`, `usage_count`, and `group` can order relevant candidates but must not resurrect an unrelated one.
- **BM25 candidate count is separate from final recommendation count.** `UserPrefs.bm25_candidate_limit` (default 30, clamped 5..100) controls how many retrieved skills are shown to the router LLM. `RecommendConfig::top_k` still controls the final hook-output ceiling. `RUNAI_BM25_TOP_K` remains a debug override for the candidate limit.
- **Behavioural feedback feeds both the hybrid re-rank and the Stage-2 candidate line.** Each recommend fetches `db.skill_router_stats(now - 90d)` + `db.skill_feedback_counts_all()` ONCE per request (never inside the candidate loop) and degrades to neutral on DB-read failure (empty maps → `feedback_factor(0,0,0,0) = 0.5`, no markers, routing continues). Two effects: (1) hybrid ranking is `bm25 * 0.35 + llm/10 * 0.45 + skill_metrics::feedback_factor * 0.20` — a harder relevance signal than the enrich-pass `llm_score` alone, since it blends real adoption rate + explicit thumbs; zero-history skills stay neutral so a fresh install is never penalised vs the old formula. (2) each candidate line appends `router::feedback_markers`: `[adopt:NN%]` (only at `chosen_sessions >= 3`, `NN = round(adopted_sessions/chosen_sessions*100)`) after `[llm:N]`, then `[fb:+P/-N]` (whenever `pos+neg > 0`). `RUNAI_FEEDBACK_DISABLED=1` is a full escape hatch: it reverts to the legacy `bm25 * 0.4 + llm/10 * 0.6` weights AND suppresses both markers (maps stay empty, skipping the fetch). Named to match the `RUNAI_BM25_*` family. `hybrid_score` / `feedback_markers` / `is_harness_message` are `pub(super)` pure functions unit-tested in `tests.rs`.
- **Harness system messages are pre-gated before any LLM call.** `router::is_harness_message(prompt)` (pure, prefix-only on the trimmed prompt) drops messages leading with `<task-notification>` / `<agent-message` / `<teammate-message` / `<local-command-`. The gate sits next to the `config.enabled` / `min_prompt_len` checks in `recommend_for_user_with_client` and returns the same empty decision — no intent wave, no router wave, and crucially NO `router_events` row, so host-injected envelopes never burn two LLM calls or pollute the adoption funnel that ranking now reads from. A prefix appearing mid-body (a real prompt quoting one) still routes.
- **`RouterMode::as_str()` is `pub(super)`** (consumed by `router.rs` + `hook_output.rs`). `RouterCallStats` is `pub(super)` in `llm_call.rs` (consumed by `router.rs`). These plus `prose_fields` / `parse_lines` / `split_mode_and_names` / `extract_at_references` / `read_project_context` are `pub(super)` so `tests.rs` reaches them by qualified path without widening the public API.

## Public API
- `struct RecommendConfig` — fields: `enabled`, `provider`, `base_url`, `model`, `api_key`, `top_k` (default 8 — final hook-output ceiling), `min_prompt_len`, `summary_lang`, `summary_lang_confirmed: bool`, `session_mode`, `session_history_limit`, `saved_providers: Vec<ProviderEntry>`, `active_provider_id: String`, `read_claude_md: bool` (default true), `skip_reminder_enabled: bool` (default false), `skip_reminder_template: String`. LLM-facing candidate count is per-user `UserPrefs::bm25_candidate_limit`. Defaults: disabled, openai-compat, DeepSeek endpoint, `deepseek-v4-flash`, top_k=8, session_mode=Oneshot, history_limit=20, summary_lang=`zh`, summary_lang_confirmed=`false`.
- `summary_lang_confirmed` — the **enrich gate**. `enrich_skills` refuses to generate ANY summary until this is `true`; it flips true only when the user explicitly picks a language via `recommend setup` or the dashboard Settings patch. A defaulted/unselected language is what produced the 2026-06 mixed-language index (47/415 summaries leaked into the SKILL.md's source language). Back-compat: `RecommendConfig::load` heals it to `true` for any pre-existing config that is `enabled` with a non-empty `summary_lang`, so upgrades don't suddenly stall a configured user's auto-enrich (derived per-load, not persisted).
- `struct ProviderEntry { id, label, kind: Provider, base_url, model, api_key }` — one row in the Settings UI provider library. Switching active copies an entry's fields into the top-level `provider/base_url/model/api_key` flat fields so LLM call sites never touch the list directly. CRUD via `RecommendConfig::{activate_provider, upsert_provider, remove_provider}`.
- `test_provider_request(cfg)` — sends a tiny real model request through the configured provider transport. OpenAI-compatible hits `{base_url}/chat/completions`, Anthropic hits `{base_url}/v1/messages`, and Claude CLI runs `claude -p`; it returns the model reply or a transport/API error without changing config or router telemetry.
- `enum Provider` — `OpenaiCompat` (default) / `Anthropic` / `ClaudeCli`.
- `enum SessionMode` — `Oneshot` (default, every call independent — prefix cache fully hits) / `Conversation` (replay this session's prior `(user, assistant)` turns from `router_events` so the LLM remembers what it already pushed; more tokens, more recall).
- `enum RouterMode` — `Compatible` (co-loadable workflow set; hook output defaults to activating all listed skills, while the main agent may ask one minimal question only for missing inputs / permissions / high-cost or irreversible risk), `Exclusive` (alternatives / ambiguity, user or main agent picks).
- `RecommendConfig::load(paths)` / `save(paths)` — toml at `~/.runai/config.toml`. Save sets `0o600` on unix.
- `RecommendConfig::effective_api_key()` — config field first, then `RUNAI_RECOMMEND_API_KEY` env.
- `recommend(mgr, prompt, transcript_path, session_id, cwd) -> RouterDecision` — anonymous compatibility wrapper over `recommend_for_user(..., None)`.
- `recommend_for_user(mgr, prompt, transcript_path, session_id, cwd, user_id)` — compatibility wrapper using `client_kind="claude"`.
- `recommend_for_user_with_client(mgr, prompt, transcript_path, session_id, cwd, user_id, client_kind)` — top-level owner-aware entry. Builds the owner-filtered candidate set (`user private ∪ library/public` by prefs), dedupes same-name rows with private shadowing public, reads the scoped prior compact-intent queue, runs Stage 1 model intent compression (deterministic fallback on failure), classifies/gates wrong-domain candidates from the compact artifact, then BM25-prefilters → `bm25_candidate_limit` candidates with `router_card` → Stage 2 router LLM call. The Stage-1 compact output is appended to `router_intent_memory` only after it is built. When `cfg.session_mode == Conversation` and `session_id` is non-empty, prior `(user_msg, llm_raw_response)` pairs from `router_events` are threaded into the Stage-2 LLM messages array.
- `struct RouterTurn { user, assistant }` — one prior router round-trip. Conversation mode replays a `Vec<RouterTurn>` ahead of the current user msg.
- `struct RouterDecision { mode, reasoning, skills }` — `reasoning` is the LLM's one-sentence "why this set" (rendered into hook output as `router 判断：...`; hidden when empty).
- `struct RecommendedSkill { name, description }` — **no path, no content**. Activation is exclusively via `runai-client activate <name>`; the router never ships SKILL.md bytes, server URLs, API keys, or filesystem paths to the main agent.
- `format_for_hook(decision, ...)` / `format_for_hook_with_session(...)` / `format_for_hook_full(decision, sid, history, server_url, user_header, skip_reminder)` — three thin wrappers around `render_hook_output`, the **single** template-driven renderer for `hook_output.md`. The `session_history`, `server_url`, `user_header`, and `skip_reminder` args are retained for caller/signature compatibility but the renderer now **ignores** them (session no-repeat removed → no recall block; skip-reminder block removed). Callers may still pass them.
- `recent_transcript_messages(path, n)` — read the last `n` user/assistant text messages from a Claude Code transcript jsonl. Tool calls/results filtered out.

## Key invariants
- **One activation path, one counting path.** Hook output tells the agent to run `runai-client activate <skill>`. That command is responsible for calling `/skills/use/{name}` or durably queuing the usage event before it prints `SKILL.md`; it also caches the whole skill bundle. There is no PostToolUse hook, no transcript-scan fallback, no `runai recommend used` self-report. The router itself **never** bumps counts; recommending ≠ adopting.
- **Agent-facing session ids are runai-owned.** Host integrations may send native session keys (`session_id`, `runai_session_id`, Pi session-file stem, Codex/Claude hook session id), but `hook_output` must only print literal `rnai_sess_*` ids generated by `runai_session_id_from_native`. Never print `$CLAUDE_SESSION_ID` or any other host-specific env var in activation commands. If no native session key exists, omit `--session-id` rather than fabricating a fake stable session.
- **Hook output never contains a filesystem path, server URL, API key, or `SKILL.md` body.** The `hook_output.md` template only references `runai-client activate <skill_name>`, `runai-client file <skill_name> <relpath>` for files inside the skill bundle, and `runai-client feedback <skill_name> --note ...` as literal commands for the agent to fill in. Runtime/user-home paths such as `~/.tool-name/...` stay local filesystem data and are not implied to live in the bundle cache. Tests assert `!out.contains("/skills/get")`, `!out.contains("/feedback'")`, and `!out.contains("Source path")`.
- **Hook output is purely positive phrased.** No "不要 Read / sm_enable / sm_install" reverse directives — `LLM` follows positive single-path instructions much more reliably than negative restrictions. The template tells the agent only what to do, never what to avoid.
- **Disabled by default.** `RecommendConfig::default().enabled == false`. Loading a missing config returns default. `recommend()` returns an empty `RouterDecision` when disabled — no LLM call, no network, no log.
- **No session de-duplication.** The router does NOT suppress, skip, or down-rank a skill because it was recommended earlier in the session — every turn is a full-quality recommend and the same skill may reappear on consecutive turns. Post-process only drops hallucinated names. (Historical: an `ALREADY_ROUTED` block used to be injected; it was removed in the Phase-5 prompt refactor.)
- **Mode + reasoning come from the LLM, defaults are safe.** First line of LLM output = `COMPATIBLE` / `EXCLUSIVE`; second line (optional) = `reasoning: ...`; remaining lines = skill names. Missing tag → `Exclusive` (safer). `COMPATIBLE` is a downstream protocol: hook output tells the local agent to activate every listed skill in order and treat it as a combo, but it may still ask one minimal question when inputs/permissions/high-cost/irreversible risk are missing. `EXCLUSIVE` means alternatives or ambiguity; image-reference single-task follow-ups are post-processed to keep the first direct match rather than surfacing several substitute generators.
- **LLM names filtered against installed skills.** Names from the model are intersected with `list_resources(Skill, _)`; hallucinated names are dropped silently.
- **`top_k = 8` is a ceiling, not a target.** `bm25_candidate_limit` controls the LLM-facing candidate list; `top_k` controls the final hook-output ceiling. `recommend_user.md` says 最小充分集合: one directly matching skill is enough for a single-point request, workflow prompts get only necessary complements, and weak/only-same-group/only-high-BM25/only-high-used candidates are omitted.
- **API key never logged or echoed.** `recommend status` shows only `set in config` / `set via env` / `missing`. Config file is `0o600`.
- **Returns success even when LLM call fails.** Errors go to stderr prefixed with `# runai recommend skipped:`; hook stdout stays parseable; main Claude continues unimpaired. Failed authenticated identity resolution is not persisted, because no router request was made. A model/provider failure after routing begins is persisted with `status='error'`.

## Prompts (templates)
All in `src/core/prompts/`:
- `recommend_intent.md` — Stage-1 intent compression **fixed system prompt** (no placeholders). Describes the input shape (`cwd:` / `agent_cli:` / `session_memory:` fields + `当前用户输入：`) and the output contract: a short BM25 artifact (`intent:` plus optional include/exclude/domain lines). It never chooses skill names or emits `EXCLUSIVE` / `COMPATIBLE`. The dynamic values live in the Stage-1 user message built by `router::build_intent_user_message`.
- `recommend_system.md` — Stage-2 router system prompt: precise intent extraction, identify-and-skip-quoted-history rule, first-step task summarisation, relevance-first admission with the **action-form-match calibration** (a request's *action* — 调研/写文档/生成/审查/规划… — being covered by a skill's `task` counts as a direct hit even when the domain is broad, as long as `not-for` doesn't exclude it; **task-type prompts give AT MOST 1 closest usable skill when an action-form-match candidate exists, and still push empty when none does** — a hard cap, not a soft "lean to at least one", because weak models drift a soft floor into "always emit one"), `not-for` rejection, constrained COMPATIBLE decision tree, fixed-combination/default-combo contract, `[llm:N] [used:N] [group:X]` tag semantics PLUS the behavioural `[adopt:NN%]` (real adoption rate) / `[fb:+P/-N]` (explicit thumbs) markers explained as harder-than-`llm` signals used only for ranking once relevance holds, output format (mode + reasoning + names), examples, and Conversation-mode guidance for using prior turns. (Session no-repeat / `ALREADY_ROUTED` handling was removed.)
- `recommend_user.md` — Stage-2 user message scaffold; the current prompt (`{USER_PROMPT}`) appears **exactly once** (truncated for the LLM), plus `{INTENT_SUMMARY}` and `{BM25_CANDIDATE_LIMIT}` for the Stage-1 compact intent / BM25 query layer, and the optional `{CWD_BLOCK}` / `{PROJECT_CONTEXT_BLOCK}` / `{HISTORY_BLOCK}` blocks; its quantity rule is 最小充分集合, not candidate padding. (The old head+tail double `{USER_PROMPT}` and `{ALREADY_ROUTED_BLOCK}` were removed.)
- Enrich and feedback prompts are constructed in `prompts.rs` because they splice the full SKILL.md and the selected summary language into a structured 6-line summary contract (task / triggers / inputs / outputs / not-for / score).
- `recommend_cwd_prefix.md`, `recommend_history_prefix.md`, `recommend_project_context.md` — supporting blocks.
- **`hook_output.md`** — single unified template for everything the main agent sees, slimmed to a short fixed body. `{MODE}`, `{REASONING_BLOCK}`, `{CANDIDATES_BLOCK}`, `{SESSION_ID_ARG}`, `{ACTIVATION_DIRECTIVE}`, `{FEEDBACK_PROTOCOL_BLOCK}` — `{SESSION_ID_ARG}` is empty when no runai session id is available. The old `{SESSION_HISTORY_BLOCK}` (已推参考池) and `{SKIP_REMINDER_BLOCK}` were removed. For `COMPATIBLE`, `{ACTIVATION_DIRECTIVE}` says to activate all candidates by default, but to ask one minimal question when required inputs / permissions / high-cost or irreversible risk are missing.

## AI summary enrichment
- `enrich_skills(mgr, limit, mode, verbose, concurrency, only_names)` — generates AI summaries in the configured `summary_lang` via the configured LLM. Each summary is stored in `resource_ai_summary` under `(owner_user_id, name)` alongside the structured recommend index: `search_doc` for BM25, `router_card` for the router prompt, plus freshness hashes. New `search_doc` rows use positive fields (`task` / `triggers` / `inputs` / `outputs`) and do not put `not-for` or the full SKILL.md into positive BM25 text; `not-for` stays visible in `router_card` for final LLM judgment. Summary feeds BM25 retriever + routing LLM, not user-facing text. **Gated**: returns an empty report immediately (with a one-line stderr nudge) unless `cfg.summary_lang_confirmed` — never enrich in a language the user never picked.
- **Enrichment is owner-aware.** Candidate enumeration goes through `enrich_candidates(db)` = `list_resources_for_user(Some(Skill), Some("*"))` — the public pool PLUS every user's private skills, so a private upload at `<data>/users/<uid>/skills/` actually gets a summary. The SKILL.md path comes from `enrich_skill_md_path(r)` = `r.directory.join("SKILL.md")` (the row's own dir), NOT `skills_dir().join(name)`; the old public-pool-only path is why private skills sat permanently "未富集". Writes use `set_skill_ai_index_scoped(name, owner_user_id, ...)` so same-named private skills do not overwrite public summaries. Both helpers are `pub(super)`, used by `enrich_skills` + `reevaluate_skill`.
- `EnrichMode::{MissingOnly, Stale, Force}` controls which skills are picked up. `only_names: Option<&[String]>` overrides `mode` to `Force` for the listed names — `runai install` / `scan` / `market-install` use this to refresh just the freshly-changed skills.
- **Language enforcement is deterministic, not prompt-only.** The enrich prompt's language directive is strengthened (`lang_directive_for` body + `lang_reminder_for` tail — last-instruction weighting for weak models, plus an explicit "translate, do not copy; only proper nouns + the `triggers` field may stay mixed" carve-out). After parse, `summary_matches_lang(summary, summary_lang)` validates **per-field** (`prose_fields` → task/inputs/outputs/not-for; `triggers` and `score` excluded). The check is script-aware, not a ratio: for `zh` a field fails if it carries kana/hangul (Japanese/Korean leak) or has zero Chinese *and* reads as a sentence (`has_en_stopword` — an English function word present); a Chinese field peppered with tool/API/path identifiers passes, and a bare identifier/CLI-flag list with no Chinese is tolerated (language-neutral, not a leak). The `task` field is the **anchor** (`is_anchor` in `field_matches_lang`): a task is always a prose description, never an identifier list, so in `zh` a zero-CJK task is ALWAYS a leak even when it dodges every stopword (`task: PDF extraction toolkit`). This anchor rule is what makes a whole-English summary structurally impossible to pass — the task line can never be language-neutral. `en` rejects any CJK/kana/hangul; `ja` requires kana; `bilingual`/free-form custom langs skip enforcement. Char-safe: `prose_fields` splits the label via `split_once([':','：'])`, never a byte index, so a full-width `：` can't panic. On mismatch the worker retries ONCE with a loud `correction` block; still mismatched → recorded as an error and **nothing is written**. `reevaluate_skill` (the feedback path) applies the same check but bails instead of retrying. Aggregate ratios are wrong here on both ends: they pass a mixed summary (one English field among Chinese ones) and false-flag a Chinese field full of identifiers.
- `find_language_mismatched_skills(mgr)` — returns the names whose stored summary fails `summary_matches_lang`. Powers `runai recommend enrich --fix-lang`: targeted re-enrich of exactly the leaked subset (forces those names, skips everything else), the cheap repair path instead of a full `--force`. Prints "nothing to do" and exits when no mismatch exists.
- `parse_enrich_response` requires a `task:` line — defensive against LLMs going off-format on huge SKILL.md.
- `reevaluate_skill(mgr, skill_name, feedback_note)` — single-skill re-enrich with explicit user feedback folded in. Updates the structured index row (`summary` + `search_doc` + `router_card` + hashes) so routing signal evolves. Triggered by `runai recommend feedback <skill> --note "..."` and the hook output's feedback protocol footer (main Claude calls it on explicit user reaction only).

## Gotchas
- Anthropic provider hits `{base_url}/v1/messages` — pass host without `/v1`. Openai-compat hits `{base_url}/chat/completions` — base_url already includes the version segment.
- The dashboard provider test is a real model request, not a base URL ping. It uses a short prompt and short timeout, so a green result means the configured model/key/base URL can answer through the selected transport.
- `Provider::ClaudeCli` stays oneshot even in Conversation mode (each call boots a full Claude Code session, so history replay would defeat the cost story).
- Hook stdout becomes part of the main Claude's prompt. The unified `hook_output.md` template + per-skill description (AI summary, not raw SKILL.md) keeps it well under Claude Code's 10 KB hook cap — even at top_k=8 the output is ~2-3 KB.
- Setup prompts for API key in plain text — there is no hidden input. Tradeoff for portability; config file gets `0o600` afterwards.
- `Provider::OpenaiCompat` works with any OpenAI-compatible service (DeepSeek, Moonshot, Groq, vLLM, etc.). DeepSeek v4-flash's prefix cache hits the static `system + candidate listing` segment of every call — `Oneshot` mode benefits most because the only thing that changes turn-to-turn is the trailing user prompt. `Conversation` mode invalidates the trailing cache as the assistant history grows, paying for the recall improvement with tokens.
- Setup wizard reads stdin line-by-line; piping `runai recommend setup < answers.txt` works for automation.
