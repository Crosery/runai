# db

> This folder (`src/core/db/`). One-liner: SQLite schema + migrations + the typed query layer for all managed metadata.

## Purpose
SQLite wrapper (via rusqlite bundled). Stores resource metadata, trash metadata, group membership, AI summaries / scores, router telemetry, users, and the per-user skill library. **Not** runtime enabled state — that lives on the filesystem.

As of the v0.11 decoupling, the former 2507-line `db.rs` is a directory: a thin `mod.rs` re-exports the public surface, the `Database` struct lives in `core.rs`, schema + every migration stays monolithic in `schema.rs`, and the CRUD is split into `impl Database` blocks per domain.

## Public surface (the API contract — external code depends on these exact paths)
- `crate::core::db::Database` — the connection wrapper + all CRUD methods.
- `crate::core::db::RouterEvent` — one router-telemetry row.
- `crate::core::db::RouterIntentMemoryItem` — one current-session short-memory row for the recommend router.
- `crate::core::db::User` — one account row (schema v15+).
- `crate::core::db::CommunitySkill` / `CommunitySort` — community-market row + sort enum (schema v16+).
- `crate::core::db::RouterModelStat` / `RouterStatsSummary` / `TimelineBucket` — aggregate stats value types. `RouterModelStat` carries per-model `avg_latency_ms` (mean over all the model's rows) + `hits` (rows with a non-empty `chosen_skills_json`) so the dashboard model-usage panel renders from one `/api/summary` call instead of paging `/api/events`.
- `crate::core::db::SkillFeedbackRow` — one `skill_feedback` row (schema v26+).
- `crate::core::db::RouterSkillStats` — per-skill router funnel counts (candidate/chosen events, chosen/adopted sessions) computed from `router_events` + `router_session_adoptions` (schema v26+).

## Invariants (load-bearing — do not break silently)
- **Schema migration runs once per (process, DB file), not per `open` (2026-07 perf fix).** `core.rs::open` records each migrated file in a process-global set and skips `init_schema` on later opens of the same file. `init_schema` stays idempotent so a fresh process still migrates on first open, and an out-of-band-upgraded DB is picked up next process start. This removed the dominant per-request cost on the dashboard, which opens one connection per request and previously re-ran the whole 26-migration batch each time (~16ms → ~1.4ms per open on a real 262MB DB). `open` also sets read-path PRAGMAs (`mmap_size`, `cache_size`). Migration failure removes the file from the set so the next open retries. Pinned by `reopening_same_db_file_stays_fully_migrated_and_usable`.
- **`schema.rs` keeps `init_schema` + every migration MONOLITHIC.** Migrations run on the first `open()` per process with no version lock; splitting them across files risks a half-applied schema. Do not factor per-migration files.
- **Row converters read columns POSITIONALLY.** `router.rs::row_to_router_event`, `users.rs::row_to_user`, and `resources.rs::collect_resources` index by `r.get(N)`. Each lives in the SAME file as the SELECTs whose column order it depends on. Never reorder a SELECT's columns without updating its converter, and never separate a query from its converter.
- **Schema migrations are idempotent** — `Database::open` must be safe to call repeatedly on an existing DB. `Database::open` also sets a short busy timeout; do not remove it unless every concurrent request write path has its own retry.
- Schema migration notes: `trash_entries`; `users`, `user_skill_library`, `resources.owner_user_id`, `router_events.user_id`; `community_skills` (PK `(uploader_uid, name)`) for the team-mode community market; structured `resource_ai_summary` with PK `(owner_user_id, name)` plus `search_doc`, `router_card`, `source_hash`, `prompt_hash`, and `format_key`; `users.session_key_hash` (issue #35) for browser sessions independent from hook api_keys; `usage_events` for activation/feedback idempotency; `router_intent_memory` (v24) for bounded recommend short memory scoped by `(session_id, user_id, client_kind)`; router_events v25 first-wave fields (`intent_llm_input`, `intent_llm_output`, `intent_status`, `intent_error_msg`, `bm25_candidates_json`) for two-stage recommend observability; `skill_feedback` (v26) — an append-only log of explicit ±1 verdicts on a skill, feeding the skill-feedback-radar metrics in `core::skill_metrics`; and the v27 covering indexes `idx_router_events_summary_cover` / `idx_router_events_permodel_cover` (see the invariant below). Owner-aware separation: `owner_user_id IS NULL` = public pool, `Some(uid)` = uid's private. Empty AI-summary `owner_user_id` means the public-pool summary; private rows use the uid so same-named public/private skills never share an index row.
- **`skill_feedback` is event-sourced, never mutated in place.** `record_skill_feedback` always inserts a new row; there is no update/upsert path. `verdict` is rejected (not clamped) unless it is exactly `1` or `-1`. `owner_user_id` follows the resources.owner_user_id convention and is matched null-safe (`IS ?`) by `skill_feedback_counts`, so a public skill and a same-named private skill never share a feedback tally; `skill_feedback_counts_all` deliberately merges across owners (per skill name) because the router blends feedback regardless of which pool instance produced it. `skill_router_stats(since_ts)` parses `bm25_candidates_json` / `chosen_skills_json` as flat JSON arrays of skill-name strings (same shape `recommend::router` writes for both columns) — a malformed row degrades to "no candidates/chosen" for that row rather than aborting the whole aggregation. Consumed by `core::skill_metrics` for the five-axis radar (`AGENTS.md` module index / `skill_metrics.rs` `//!`).
- **`router_stats_summary[_filtered]` aggregations MUST stay index-only covering scans (2026-07 `/api/summary` 17s cold-read fix, schema v27).** `router_events` rows are very wide (`llm_input` caps at 64 KB, `hook_output`/`llm_raw_response`/`user_prompt` several KB each), so a full-table SCAN for the summary `COUNT`/`SUM(total_tokens)`/`AVG(latency_ms)`/`GROUP BY model` faults in the entire ~260 MB table via random reads — measured ~17s cold on a real 7k-row install, ~0s once the OS page cache is warm; `/api/summary` is polled every 5s by every open Overview tab so the cold hit stalls the dashboard. v27 adds two narrow covering indexes (~400 KB each vs the 260 MB table): `idx_router_events_summary_cover(ts, user_id, status, model, latency_ms, total_tokens, prompt_tokens, completion_tokens, reasoning_tokens)` covers the main aggregation + the ok-only `AVG(latency_ms)`; `idx_router_events_permodel_cover(model, ts, user_id, total_tokens, latency_ms, chosen_skills_json)` covers the `GROUP BY model` query (which also computes `hits` from `chosen_skills_json` + per-model `AVG(latency_ms)`) — `model` leads so the GROUP BY needs no table sort, and the narrow `chosen_skills_json` is INCLUDED so the hits CASE never touches the wide rows. Bench (copy of the real 262 MB / 7056-row DB, `sudo purge` cold): full summary trio ~1.05s → ~5ms cold; main aggregation alone 0.505s → 0.005s. `EXPLAIN QUERY PLAN` must report `SCAN … USING COVERING INDEX …` for both — pinned by `tests.rs::router_stats_summary_queries_are_index_only_covering_scans`. If you add a column to either summary query, add it to the matching index or the scan silently falls back to a full-table read and the 17s regresses. Do NOT drop `chosen_skills_json` from the per-model index — it's the only reason the hits count stays index-only.
- **`skill_router_stats` does exactly two queries total, never N+1 (2026-07 fix).** It used to run one `router_session_adoptions` COUNT query PER `(skill, chosen_session)` pair discovered in the `router_events` scan — on a real install with thousands of events that was thousands of synchronous SQLite round trips inside a single call, the dominant cost behind `server::stats_cache`'s existence. It now bulk-reads the entire (unfiltered) `router_session_adoptions` table once into an in-memory `HashSet<(session_id, skill_name)>` and checks membership against that instead. `router_session_adoptions` is deliberately NOT windowed by `since_ts` here — `record_session_adoption` upserts one row per `(session_id, skill_name)` ever adopted, so the table stays far smaller than `router_events` and a full scan of it is both cheaper and simpler than trying to time-bound it without risking dropping adoptions recorded slightly after the window-edge `router_events` row that produced them. `router_events(ts)` already has `idx_router_events_ts` (schema v5) so the primary scan is index-backed; no schema change was needed for this fix. Benchmarked at 5,000 `router_events` rows × 30 BM25 candidates each (`tests.rs::skill_router_stats_bench_5000_events_x_30_candidates`): ~204ms → ~95ms in a debug build for this specific fixture (three always-chosen skills out of 30; roughly half the delta is pure per-row query overhead eliminated, the remainder is JSON-parsing cost shared by both old and new code and unrelated to this fix). Real installs with broader skill/session fan-out saw multi-second stalls before this fix. Do not reintroduce a per-`(skill,session)` query inside the adoption-counting loop.
- Legacy table names (from the `skill-manager` era) are **kept alive** for rollback safety; new code writes only to the renamed tables.
- `insert_resource` round-trips `Source` via `to_meta_json` / `from_meta_json` and preserves usage columns on conflict — re-scan/update paths must not zero usage. PK `id` already encodes the owner (`u:<uid>:` prefix from `Resource::generate_id`) so same `(source, name)` across users do not collide.
- **`dedupe_skills_by_name` groups by `(name, owner_user_id)`, never `name` alone.** Name-only grouping would collapse a public skill and a different user's same-named private skill (or two users' privates) into one row and delete the loser's directory reference — cross-owner data loss against the owner-pool invariant. Uses SQLite's null-safe `owner_user_id IS ?` so a bound NULL matches public rows and a bound uid matches that user exactly. Public same-name rows still collapse together (the legitimate local-install + later-adopt case).
- **`library_remove_for_all` / `cleanup_orphan_library_entries` are public-pool-aware (C4, scan_findings.md).** `user_skill_library` only ever tracks public-pool subscriptions (private skills the owner installs are never rows here). Because the owner-pool design lets a private skill share a name with an unrelated public one, both sweeps must scope to `owner_user_id IS NULL`: `library_remove_for_all(name)` deletes only when NO public row of that name remains (`AND NOT EXISTS (... owner_user_id IS NULL)`), so trashing a PRIVATE skill that shares a name with a public one does NOT wipe every other user's subscription to the public skill; `cleanup_orphan_library_entries` counts a name as "still exists" only via a public row, so a subscriber's public `foo` being trashed while a different user's private `foo` survives still sweeps the now-orphan row. Callers (`trash_resource`, `delete_user_cascade`, `doctor --fix`) `delete_resource` first, so for a genuine public trash the guard passes and subscribers are swept. Do NOT drop the `owner_user_id IS NULL` filter back to name-only. Pinned by `library_remove_for_all_spares_public_when_private_same_name_gone` + `cleanup_orphan_library_entries_is_public_pool_aware` in `tests.rs`.
- Trash payloads are stored as JSON `TrashEntry` blobs; new `TrashEntry` fields must stay serde backward-compatible. `owner_user_id` was added with `#[serde(default)]` so pre-v15 payloads still decode (owner surfaces as `None`).
- **Activation ACK is atomic.** `record_activation_usage_event` is the only correct way to ACK `/skills/use/{name}`. It wraps `usage_events` insert/dedupe, `resources.usage_count` bump, and `router_session_adoptions` write in one `BEGIN IMMEDIATE` transaction. A server ACK must never leave behind only the idempotency row without the usage side effect.
- **Recommend intent memory is bounded by the caller's limit and stores first-wave intent artifacts.** `append_router_intent_memory(session_id, user_id, client_kind, memory, limit)` stores at most one capped short-memory row per call, then trims that exact `(session_id, user_id, client_kind)` scope by dropping oldest rows beyond `limit`. The caller must pass the compact Stage-1 `intent_llm_output`, not raw user prompt text. `limit == 0`, empty `session_id`, or empty memory is a no-op. Do not merge scopes: Pi/Codex/Claude/OpenCode memory must not cross-contaminate even if they share a native session string.
- `Database::conn` is `pub(super)` — sibling submodules' `impl Database` blocks access `self.conn`; it is NOT part of the public API. Use `conn_ref()` for the (rare) crate-internal raw-SQL escape hatch.
- **Fixed regression (github.com/Crosery/runai/issues/33)**: `router.rs::router_event_by_id` and `router.rs::router_events_since_ordered` used to omit the trailing `user_id` column from their SELECTs while `row_to_router_event` still read it positionally — both silently returned `user_id: None` regardless of the stored value. Same failure class as the historical "`router_event_by_id` 漏 user_id 列" incident, recurring in the same function. Both SELECTs now include `user_id`; pinned by `router_event_by_id_preserves_user_id` and `router_events_since_ordered_preserves_user_id` in `tests.rs`. If either query is touched again, keep its column list in sync with `row_to_router_event`'s positional reads (see the INVARIANT comment at the top of `router.rs`).

## Gotchas
- Tests must serialize DB access with `--test-threads=1` — rusqlite bundled SQLite gets upset under parallel I/O on the same file. CI already does this.
- No connection pool — one `Database` == one connection, pass `&Database` through call stacks. Don't clone.
- `mod.rs` has a child `mod core;` while `crate::core` also exists — `use core::Database;` in `mod.rs` resolves to the local child module (it's an in-scope `mod`), not `crate::core`. Don't "fix" it to `crate::`.
- `schema_version()` is the contract between the app and the DB — bump it whenever you change the schema.
