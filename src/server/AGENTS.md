# server — LLM module guide

> This folder (`src/server/`). One-liner: axum HTTP dashboard + remote-hook + multi-user API, one file per route family.

## Public surface (stable — external code depends on these paths)
The entire crate-visible surface is exactly four items, re-exported from `mod.rs`. Everything else is `pub(super)` (module-internal) — there is no other public API.
- `crate::server::serve(host: &str, port: u16) -> Result<()>` — async entrypoint with default owner mode + no TLS. Used by `ensure_running`'s detached spawn so the auto-spawned dashboard stays single-user. Otherwise prefer `serve_with`.
- `crate::server::serve_with(host, port, mode: ServerMode, tls_cert: Option<PathBuf>, tls_key: Option<PathBuf>) -> Result<()>` — canonical entrypoint that runs `server_mode::validate_startup` first (team + non-loopback + no TLS = bail) and stamps `mode` / TLS material onto `AppState`. Called from `cli::dispatch` for `runai server`.
- `crate::server::ensure_running(host: &str, port: u16) -> Result<EnsureStatus>` — idempotent "is the dashboard up, if not spawn it detached" helper. Called from the TUI auto-spawn path and `cli::dispatch`.
- `crate::server::EnsureStatus` — `{ AlreadyRunning, Started }` enum returned by `ensure_running`.

Consumers: only `src/cli/dispatch.rs` (5 call sites). The split preserved every path — zero consumer edits.

## Invariants (load-bearing — do not break silently)
- **Data dir resolution honors `RUNE_DATA_DIR` (issue #24).** `serve_with` builds `AppState.db_path` from `AppPaths::resolve()` (env precedence `RUNE_DATA_DIR` > `SKILL_MANAGER_DATA_DIR` > default), and the standalone reads in `market.rs` / `market_preview.rs` / `prefs.rs` do the same. Every request handler that derives its data root from `state.db_path.parent()` is therefore consistent automatically. The handlers that construct `SkillManager::new()` (market/market_github/recommend/skills/admin) are also consistent because `new()` now resolves via `resolve()`. Do NOT reintroduce `AppPaths::default_path()` anywhere in this folder — it is env-blind and would resplit the server's data dir from the `recommend enrich` child it spawns.
- **`mod.rs` holds the `include_str!` consts at `../../`** (`src/server/mod.rs` is one dir deeper than the old `src/server.rs`, so `../web/...` → `../../web/...`, `../scripts/...` → `../../scripts/...`). Five `CLIENT_*` consts feed `install.rs`; `INDEX_HTML`/`APP_JS`/`APP_CSS` feed `app.rs`.
- **Path-traversal guards moved verbatim.** `skills.rs::api_skill_file` and `handle_skill_file` both `canonicalize()` the skill_dir root and the joined target then assert `target_real.starts_with(&root_real)` before reading. Never relocate the canonicalize/`starts_with` check away from the handler that joins the user-controlled `?path=` / `{*path}`.
- **`serve_index` cache-bust string-replace** rewrites the literals `"/app.css"` and `"/app.js"` to append `?v=<BUILD_ID>`. If web assets are ever split into `/css/*` / `/js/*`, this replace MUST be extended to each new URL (see `docs/decoupling/PLAN.md` §6c) — there is no compile gate for a stale-cache bug.
- **Enrichment 3-state lives in `enrich_state` (in-memory), not the DB.** `SkillRow.enrich_status` on `/api/skills` is `"enriched"` (that resource's `(owner_user_id, name)` summary row is non-empty), `"enriching"` (name in the `enrich_state` in-flight registry, TTL 300s, and no fresh summary has landed yet), or `"unenriched"`. `api_skills` computes it per visible resource using the owner-aware AI index; a same-named private skill never borrows the public summary. `market::spawn_enrich` (`mark_enriching`) and `recommend.rs::handle_feedback` (`enrich_state::try_claim`, the race-free atomic variant) are the two writers of the in-flight mark — every server-side enrich trigger (upload / install / market_github / the file watcher / a `/feedback` vote) flips the tag. The registry is process-global and resets on restart by design; genuinely-pending skills are re-triggered by the watcher or complete and show 已富集. `SkillsResponse.enriching` is the in-flight count for the hero delta.
- **Shared private helpers live in exactly one home.** `state.rs` owns `current_user`/`require_user`/`current_owner_id`/`resolve_skill_dir`/`resolve_skill_dir_scoped`/`require_admin`/`resolve_view_user` + `AppState`; siblings import via `use super::state::X`.
- **`/skills/get|file|bundle` are anonymous by design; the public pool is world-readable through them (A2).** These three are the recommend-hook's credential-less compat surface (an external Claude Code hook with no Bearer still fetches public skills). They carry only the rate-limit layer, NOT the `private_data_locked → require_user` carve-out `api_skills` has. That means **every public-pool skill's full content is readable by anyone who can reach the port** — this is intentional (team-server operators must treat public skills as non-secret), not a hole. The dashboard `/api/*` JSON surface stays auth-gated; only these content routes are open.
- **`/skills/use/{name}` is the idempotent activation usage endpoint.** New `runai-client activate` calls it with `X-Runai-Event-Id` before printing cached `SKILL.md`. The handler must insert the idempotency row, increment the resolved resource's `usage_count`, and record session adoption in one SQLite transaction via `Database::record_activation_usage_event`; never split those side effects into separate writes. Missing event id returns 422, same id + same payload returns 200 no-op, same id + different payload returns 409 with an empty-details body. Non-empty `session_id` must already be a runai-owned `rnai_sess_*` id; host-native ids are normalized before hook output and rejected here. Missing Bearer keeps the anonymous public lane; a present but stale Bearer returns 401 empty and must not fall back to anonymous.
- **`/recommend` has two auth lanes, but stale Bearer is never anonymous.** No `Authorization` header keeps the legacy anonymous hook lane alive. A present but malformed / unknown / disabled Bearer returns `200 + empty text/plain` before routing and writes no `router_events` row. This fail-closed rule is load-bearing: the api_key still rotates on script re-login (`rotate_api_key:true`), logout-everywhere, and admin password reset (browser login no longer rotates — issue #35), so an old `~/.runai-identity` must not bypass per-user `UserPrefs.prompt_injection_flags` by falling back to anonymous defaults. The payload's `client_kind` / `host_kind` is part of the router scope: it is folded into the native-session hash before `rnai_sess_*` derivation and passed to `recommend_for_user_with_client`, so Pi/Codex/Claude/OpenCode short-memory queues stay separate.
- **`/feedback` requires `require_user` (issue #26) — no anonymous/forged-header lane like `/recommend`'s.** Unlike `/recommend`, `/feedback` triggers a real LLM call (`reevaluate_skill`) and rewrites a skill's AI summary/score, so it has no legacy anonymous compat window: a missing/invalid Bearer or session cookie gets `401 + empty body` (via `(StatusCode::UNAUTHORIZED, "").into_response()`, deliberately NOT `ApiError::Unauthorized`'s `{"error":"unauthorized"}` JSON — matches the anti-enumeration style of `empty_404`). In owner mode this is a no-op gate (the synthetic implicit-admin `current_user` short-circuit means every caller is already "authenticated"); team mode is where this actually blocks anonymous callers. The response's "applied by" attribution is always `user.username` from the authenticated `User` row — the `X-Runai-User` header (still legitimately read by `/recommend` for session-id prefixing) is NOT read by `/feedback` at all, because it is fully client-controlled and was previously trusted verbatim for that attribution field. `tests/feedback_auth_e2e.rs` pins all three: anonymous → 401 empty, forged header without Bearer → still 401 empty, valid Bearer → 200 with the real username (never the forged header value).
- **`/feedback` has two independent bodies gated by the optional `verdict` field (skill-feedback-radar), and re-enrich is now ALWAYS asynchronous.** No `verdict` key at all = the legacy note-only path: existence is checked synchronously (`find_resource_by_name_for_user(.., Some("*"))`, mirroring `reevaluate_skill`'s own internal `enrich_candidates` scope) and a miss bails "skill not found: ..." → mapped to `400` + text/plain, same wire contract as before (pinned by `tests/router_skill_lifecycle_p1c0.rs::feedback_returns_400_for_unconfigured_router_or_missing_skill`). When `verdict` IS present (`1`/`-1` or case-insensitive `"good"`/`"bad"`; anything else is `400`), the handler resolves the skill in the CALLER's own owner scope (`find_resource_by_name_for_user`, public ∪ own private, admin `"*"`) — a miss is `404` empty body, matching the anti-enumeration style used elsewhere in this file. On a hit it appends one row to `skill_feedback` via `Database::record_skill_feedback` (event-sourced, never gated by the `X-Runai-Event-Id` idempotency header — a repeat vote is just another log row, by design). **Every request that successfully records feedback — verdict-only, note-only, or both — then queues a re-enrich, unconditionally and asynchronously**: it claims `enrich_state::try_claim(skill)` and, if the claim succeeds, spawns `recommend::reevaluate_skill` on a detached `std::thread` (`recommend.rs::spawn_reevaluate`) and returns immediately; a verdict with no `note` synthesizes a one-line positive/negative signal so the LLM prompt has something concrete. The JSON response (`FeedbackAck`) carries `reenrich: "queued"` (this call won the claim) or `"already-running"` (another vote's re-enrich is still in flight for this skill within the TTL window — no duplicate LLM call spawned, but the vote was still recorded) — this replaces the old synchronous "llm_score X → Y" response text; `message` still contains the substring `"feedback applied by {username}: {skill}"` so pre-existing substring-matching callers (dashboard, `runai-client`) are unaffected. The `X-Runai-Event-Id` idempotency header (when present) still gates the re-enrich TRIGGER only (First → queued, Duplicate → 200 no-op, Conflict → 409); it never gates the `skill_feedback` DB insert. A `spawn_reevaluate` failure (including "recommend not configured") only `tracing::warn!`s — the client already got its 200, and the `enrich_state` mark is left in place to expire via TTL rather than cleared, so the dashboard tag stays 富集中 instead of silently reverting. Do not move the skill-existence check inside `reevaluate_skill`'s own resolution for the verdict path — that lookup is public-pool-and-admin-only (`enrich_candidates` uses scope `"*"`) and would let a non-admin record feedback against another user's private skill they can't otherwise see.
- **`GET /api/skill/{name}` also carries `enrich_status`** (`"enriched"`/`"enriching"`/`"unenriched"`), computed identically to `api_skills::SkillRow.enrich_status` but from the resolved resource's own owner-scoped `resource_ai_summary` row — lets the dashboard detail page poll this single endpoint after a `/feedback` vote and watch the tag flip 富集中 → 已富集 without a separate `/api/skills` call.
- **The disk-fallback in `resolve_skill_dir_scoped` must never serve a private skill (A1).** After the owner-scoped DB lookup misses, the bare on-disk fallback `paths.skills_dir().join(name)` is gated: it only returns when NO private row owns that name (`find_resource_by_name_for_user(Skill, name, Some("*"))` has `owner_user_id.is_none()` or no row). Without this guard a stray public-pool dir shadowing a private DB row (the live `agent-browser`: private row + leftover `<data>/skills/agent-browser`) is handed to anonymous callers. Do NOT drop the `private_shadow` check; `tests/anon_skill_leak_e2e.rs` pins it (private→404, genuine public→200).
- **`resolve_skill_dir_scoped` sanitizes the route `name` BEFORE any lookup or join (C1).** The very first thing the function does is `if !paths::is_safe_skill_name(name) { bail }`. The route `name` is user-controlled and is joined onto `skills_dir()` in the disk-fallback above; without the guard, `name=".."` (sendable as `%2e%2e`, which axum's Path extractor decodes to `..` after matchit routes on the raw segment — reqwest/`url` normalizes it away, so only a raw client can smuggle it) makes `skills_dir().join("..")` resolve to the whole `<data>` dir, which `.exists()`, so the three anonymous content routes (`/skills/get|file|bundle`) tar/read the ENTIRE data dir incl. `runai.db` (argon2 password + api_key hashes) and every user's private pool. `is_safe_skill_name` rejects `.`/`..`/`..`-substring/`/`/`\`/NUL/control chars (looser than `is_safe_user_id`: skill names may be unicode + contain interior dots). One guard covers every caller (`/skills/get`, `/skills/file`, `/skills/bundle`, `/api/skill/*`). Do NOT move the check downstream of the join — the join is the sink. `tests/skill_name_traversal_e2e.rs` pins it (raw `%2e%2e` → 404, real skill → 200).
- **Admin-gated `?owner=<uid>` on skill detail/files/file** (dashboard "用户库" drill-in). `api_skill_detail` / `api_skill_files` / `api_skill_file` accept an optional `owner` query param. When the viewer **is admin** and `owner` is non-empty, resolution is pinned to that user's pool (`api_skill_detail` uses scope `Some(uid)` instead of `"*"`; the file endpoints go through `state::resolve_skill_dir_scoped`). A **non-admin's `owner` param is ignored** — they keep their own scope (no privilege escalation). This is the only way to disambiguate same-named private skills across users; without it `"*"` picks the freshest and the file endpoints (keyed off the admin's OWN uid via `resolve_skill_dir`) can't find another user's private skill at all. `resolve_skill_dir` is the `resolve_skill_dir_scoped(.., None)` shorthand, so every pre-existing caller is byte-identical. `error.rs` owns `ApiError`. `recommend.rs` owns `guess_server_url` (used by `skills.rs` + `install.rs`). `market.rs` owns `spawn_enrich` + `InstallResp` (used by `market_github.rs`). Keep them `pub(super)`, never `pub` — widening leaks the API.
- **Tenant isolation rules** (`resolve_view_user` / `current_owner_id` / `resolve_skill_dir`) are unchanged from pre-split: compat carve-out when `users` table empty, non-admin forced to own scope, admin global-by-default, private rows shadow public for the owner. `/api/event/{id}` returns 404 (not 403) on cross-tenant to block id enumeration.
- **Server mode gates the register/install surface** (PLANNING §1.1 + §1.2). `state.mode` is the source of truth. `auth.rs::api_register` returns 403 when `state.mode == ServerMode::Owner`. `install.rs::handle_install_script` / `handle_install_ps1` / `handle_uninstall_script` / `handle_uninstall_ps1` all return 404 (empty body) when owner mode — single-user self-serve has no remote client surface. In team mode they call `render_install_script(template, mode, server_url)` which (a) strips every `# === RUNAI_SECTION:<other>-only START === ... END ===` block (marker grammar is line-based and identical for `.sh` + `.ps1` because both use `#` line comments), (b) drops the START/END marker lines for the requested mode too so the served file is clean, (c) replaces `{SERVER_URL}` with the request origin via `recommend::guess_server_url`. Both client install scripts (`scripts/runai-client-install.sh` + `.ps1`) wrap their team-flow content in `# === RUNAI_SECTION:team-only ... ===` and reserve an empty `# === RUNAI_SECTION:owner-only ... ===` scaffold for symmetry. Do NOT re-derive the mode from "are there users registered?" — that's exactly the implicit recovery model the flag replaces.
- **`POST /api/community/upload` is admin-only (issue #29).** It's the direct-to-community-pool write and it bypasses the draft → enrich → publish-request → approve workflow below, so a non-admin caller now gets `403 Forbidden` (`require_admin`, same as every other admin-gated route). It is NOT called internally by the approve flow — `admin.rs::api_admin_publish_approve` does its own `copy_dir_recursive` + `upsert_community_skill`, so this endpoint has no remaining internal caller; it stays mounted purely as an admin convenience (seeding the pool directly / restoring a skill from backup) and is exercised by `tests/community_market_e2e.rs::direct_community_upload_requires_admin`. Every user-facing entrypoint — `runai-client upload` (bash), CLI `runai community upload` (`cli/handlers/community.rs`), and the TUI Community-tab upload picker (`tui/app/market_tab.rs::do_upload`) — posts to `/api/users/me/skills/upload` instead; do NOT point any new client at `/api/community/upload`.
- **Publish workflow (PLANNING §1.4 rewrite)**: user uploads land in the caller's PRIVATE pool with `publish_status='draft'` via `POST /api/users/me/skills/upload` (`private_upload.rs::api_user_skills_upload`). Each upload immediately fires `market::spawn_enrich(&[name])` (best-effort, fire-and-forget). User asks `POST /api/users/me/skills/{name}/publish-request` to move draft → pending; the handler refuses (400) when that private resource's `(owner_user_id, name)` `resource_ai_summary.summary` is empty (enrich gate). Admin sees pending rows via `GET /api/admin/publish-requests` (`admin.rs::api_admin_publish_list`, joins `users` + owner-scoped `resource_ai_summary`), then either `POST .../approve` (pending → approved, runs `copy_dir_recursive` from `<data>/users/<uid>/skills/<name>/` to `<data>/community/<uid>/<name>/`, upserts `community_skills`) or `POST .../reject` with a non-empty `reason` (pending → rejected, writes `resources.publish_reason`). The 4-state machine is monotonic in normal flow but tolerates rejected → pending on a re-submission so users can iterate. `Database::set_publish_status(_with_reason)` is the only writer of `publish_status` — never `UPDATE resources SET publish_status` directly. Public-pool rows (`owner_user_id IS NULL`) keep `publish_status='draft'` and are ignored by every publish handler.
- **Owner mode dashboard cut (PLANNING §1.1)**: `state.rs` carries a process-global `SERVER_MODE_VAL` atomic set inside `app.rs::serve_with` BEFORE the `AppState` is built. `state::current_user` returns `Some(synthetic_owner())` and `state::private_data_locked` returns `false` whenever `server_mode() == ServerMode::Owner`, so the 41 `require_user` / `require_admin` / `current_owner_id` call sites keep their existing signatures — adding a new authenticated route requires zero owner-mode plumbing. The synthetic identity is `User { user_id: "owner", username: "owner", is_admin: true, disabled: false, .. }` with empty `password_hash` / `api_key_hash` / `prefs_json` (never persisted). `auth.rs::api_me` special-cases the sentinel `user_id == "owner"` to skip `library_count` (synthetic owner has no DB row) and stamps `MeResp.mode` with the runtime mode string for the frontend. `app.rs::serve_index` patches `<body class="theme-github"` → `class="theme-github mode-owner"` exactly once when owner mode is active; team mode body is byte-identical. The bundled `web/css/13-owner-mode.css` is wired into `mod.rs::APP_CSS` concat and hides team-only chrome under `body.mode-owner`: `#account-pill` / `#auth-modal` / `#library-scope-bar` / `.market-source-tab-btn[data-mtsource="community"]` / `#market-community-pane` / `#community-detail-modal` / `.settings-section.admin-block:has(#admin-users-rows)`. Router 总闸门 + 运营商 panes stay visible — owner is the implicit admin and still wants to configure routing. Do NOT introduce per-handler `state.mode` reads as the owner-mode short-circuit path; the atomic + helper-level short-circuit is intentional, so new routes "just work" in owner mode. Do NOT shrink the `mode-owner` CSS list without grepping `web/index.html` to verify the element is truly team-only — `:has(#admin-users-rows)` for instance is load-bearing because it scopes the hide to exactly the user-management section without touching neighbouring `.admin-block` siblings.
- **TLS bind path (PLANNING §2.3 item 2)**: `serve_with` runs `server_mode::validate_startup(mode, host, tls_cert, tls_key)` before binding; team + non-loopback + no TLS → bail at startup. When both `tls_cert` AND `tls_key` are present (any mode), the bind switches from `axum::serve(TcpListener)` to `axum_server::bind_rustls(addr, cfg)` — the rustls cert + key are loaded via `tls::load_rustls_config`. Owner mode can opt in to TLS too; it is not gated on team mode. Both code paths attach `into_make_service_with_connect_info::<SocketAddr>()` so the rate-limit middleware sees the peer IP.
- **Anti-explore + uniform 404 (PLANNING §2.3 item 4)**: `app.rs::empty_404` is wired as the global fallback (`.fallback(empty_404)`) AND explicitly mounted on every known self-describing-API probe path (`/openapi.json` / `/openapi.yaml` / `/swagger` / `/swagger.json` / `/swagger-ui*` / `/docs*` / `/api-docs*` / `/__schema` / `/graphql` / `/redoc`) via `any(empty_404)` so HEAD/POST/OPTIONS probes return the same `404 + empty body` as GET. Do NOT add diagnostic JSON, `Content-Type`, or `X-*` headers to `empty_404` — the contract is "every miss is bytewise the same response so an attacker cannot distinguish unknown-path from auth-required from internal-error".
- **TLS fingerprint endpoint (PLANNING §2.3 item 3)**: `GET /api/tls/fingerprint` returns `{"fingerprint":"<64-char lowercase hex>"}` (SHA-256 of leaf cert DER) when `AppState.tls_cert` is set, else `404 + empty`. Unauthenticated by design: an attacker on the wire already sees the cert on TLS handshake, exposing the fingerprint over HTTP adds no info. The client install script writes this to `~/.runai-server.json` at install time; the hook wrapper re-fetches it on every prompt and refuses to forward if the live value diverges from the pinned one.
- **Rate-limited sub-routers (PLANNING §2.3 item 6 + C2)**: `/auth/login`, `/api/community/upload`, `/api/users/me/skills/upload`, `/skills/get/{name}`, and `/skills/use/{name}` each live in their own `Router::new().route(...).layer(middleware::from_fn(...))` sub-router that is `.merge()`d into the main router. Mounting via sub-router (not `.layer` on the main router) confines the limit to that path family — no risk an unrelated handler gets throttled by accident. Over-quota responses are produced by `rate_limit_layer` ahead of the handler, so even malformed requests count toward the bucket. **`/api/users/me/skills/upload` MUST stay in `private_upload_router` (C2 — scan_findings.md), not mounted bare on the main router**: it is the user-facing private-pool upload path (issue #29 made `/api/community/upload` admin-only), and each call extracts a tar.gz + forks a `runai recommend enrich` LLM child, so an unthrottled non-admin loop is a disk-fill + LLM-spend DoS. It has its own `PrivateUpload` bucket namespace (10/hr/user, same quota as community upload but a separate counter). `/skills/use/{name}` reuses the skills-get limiter because it is the client activation usage endpoint and can be hit on every agent prompt.
- **Admin password reset rotates the api_key (`POST /api/admin/users/{user_id}/reset-password`).** `admin.rs::api_admin_reset_password` is admin-gated (`require_admin` → 401/403), 404s an unknown `user_id`, 400s a `new_password` failing `validate_password` (min 6). It writes a fresh argon2 `password_hash` AND rotates `api_key_hash` in one `Database::set_user_credentials` UPDATE — a reset implies the old secret is compromised, so every previously-issued Bearer (browser cookie / `~/.runai-identity`) dies and the user must `/auth/login` with the new password to mint a new key. The freshly-minted key is NEVER returned in the response (`AdminResetPasswordResp` is just `{user_id, username}`) — it is only obtainable by logging in. Admin may reset their own account. This is the same credential-write path as the local CLI `runai admin reset-password` (`cli/handlers/admin.rs`); both go through `set_user_credentials`, so a reset via either surface behaves identically. `tests/admin_reset_password_e2e.rs` pins the wire contract (new-pw-logs-in / old-pw-401 / old-key-401 / non-admin-403 / short-pw-400 / unknown-404).
- **Session model: independent session token, login never rotates the api_key unless asked (issue #35, schema v22)**. A plain `POST /auth/login` (dashboard) verifies the password, mints an `rnai_sess_...` token (`core::auth::new_session_token`), stores its SHA-256 in `users.session_key_hash` (one slot per user — a new login replaces the previous session), sets it as the `runai_session` cookie, and returns NO api_key; `api_key_hash` is untouched, so a browser login never revokes installed hook clients (the pre-#35 model rotated on EVERY login and silently killed every `~/.runai-identity`). `POST /auth/login` with `"rotate_api_key": true` — sent only by the install scripts, which persist the key to disk — keeps rotate-and-return semantics and does not touch the session slot (an active browser session survives a script re-login). Auth lanes in `state::current_user`: Bearer → `api_key_hash` ONLY (a leaked cookie token must never work as a hook credential); cookie → `session_key_hash` first, then `api_key_hash` fallback for pre-#35 cookies that carried the raw key. `api_logout` only clears the current browser's cookie (non-revoking). `api_logout_everywhere` (`POST /api/me/logout-everywhere`, auth-required) is the real revoke: rotates the api_key AND nulls `session_key_hash`, then clears the cookie. Admin password reset (`set_user_credentials`) also clears the session. `tests/login_session_rotation_e2e.rs` pins the whole matrix; `tests/session_logout_e2e.rs` pins the logout-everywhere revoke.
- **Client installers validate existing identity before reusing it.** `scripts/runai-client-install.{sh,ps1}` probe `/api/me` with the stored `~/.runai-identity` key; only HTTP 200 is reused. Any stale / malformed key is removed and the script signs in again. This pairs with `/recommend` fail-closed auth so reinstalling repairs hook identity after browser login rotation.
- **Login failure is uniform (PLANNING §2.3 item 5)**: `auth.rs::api_login` returns `Response` (not `Result<Json<>, ApiError>`) and routes all three failure modes (`find_user_by_username = None`, `user.disabled`, `verify_password = false`) through `login_failure()` which produces `401 + {"error":"invalid_credentials"}`. Do NOT introduce a "user not found" vs "wrong password" distinction in the wire response — log it server-side if you need to, but the body must stay the canonical `LOGIN_FAILURE_BODY` constant so an attacker cannot enumerate accounts via response diffing.
- **Compat carve-out for telemetry / skill browse is "cold server only" (PLANNING §2.3 item 5)**: `state::private_data_locked(db)` returns `true` once any `users` row exists OR any `router_events` row exists. `resolve_view_user` (used by `api_summary` / `api_events` / `api_timeline` / `api_event_by_id`), the inline check in `api_skills` / `api_skill_detail`, AND `prefs.rs`'s admin gate on `api_get_settings` / `api_post_settings` / `api_upsert_provider` / `api_delete_provider` / `api_activate_provider` / `api_test_provider` all consult this SAME function. A previously owner-mode/team server with accumulated `router_events` history but an emptied `users` table therefore cannot leak rows to anonymous callers on ANY of these endpoints — the carve-out only opens the very first dashboard visit on a fresh deployment. Do NOT reintroduce a standalone `db.list_users().is_empty()` check anywhere as a stand-in for this gate (issue #32: `prefs.rs` briefly had its own copy that ignored `router_events`, reopening `/api/settings` writes — including provider `api_key` — on a "users deleted, events remain" server even though telemetry endpoints correctly 401'd). Anonymous reads/writes of any non-empty tenant surface must 401.
- **Telemetry DTO exposes auth lane, not identity.** `telemetry.rs::EventJson.authenticated` is `router_events.user_id IS NOT NULL`. The dashboard uses it to explain why per-user prompt toggles did or did not apply; it must remain a boolean and must not serialize the raw `user_id`. EventJson also exposes the two-stage recommend artifacts (`intent_llm_input`, `intent_llm_output`, `intent_status`, `intent_error_msg`, `bm25_candidates`) so Activity detail can show Stage 1 intent recognition separately from Stage 2 router input/output.
- **`api_skill_detail` computes the skill-feedback-radar from real telemetry, scoped to the SAME owner scope the handler already resolved the skill in.** `radar` blends `core::skill_metrics::compute_radar` over: `Database::skill_router_stats(since_ts)` (90-day window) for adoption/precision, `Database::skill_feedback_counts(name, resource.owner_user_id)` for rating, `llm_score` for quality, and `resource.usage_count` against the corpus `max_usage_count` for heat. `radar_avg` is the mean of that same formula over every OTHER skill in `owner_scope` that has a non-empty AI summary (`skill_ai_index_all_by_resource_key`) — reusing `owner_scope` (not a bare `"*"`/`None`) is load-bearing: it's what stops a non-admin's average from folding in another user's private router/feedback counts. `Database::recent_skill_feedback` is NOT owner-scoped at the SQL layer (it filters by `skill_name` only, so a public skill and a same-named private skill share one result set) — `api_skill_detail` filters the returned rows to `f.owner_user_id == resource.owner_user_id` before taking the top 10, so `feedback_recent` never bleeds across owner pools. `feedback_recent[].user_id` is `null` unless the viewer `is_admin` (same admin-only-see-authors rule as `EventJson.authenticated`, but here at author-identity granularity, not just a boolean).
- **Provider testing is a model request, not a URL ping.** `prefs.rs::api_test_provider` is admin-gated, loads the saved provider by id, then calls `recommend::test_provider_request`. Success means the configured provider/model/key answered a tiny LLM prompt through the selected transport. Transport/API failures return `200 + {ok:false,error}` so the Admin pane can show the model failure inline instead of treating it as a broken dashboard endpoint.
- **Every DB-touching handler MUST run inside `tokio::task::spawn_blocking` (2026-07 blocking-runtime audit).** `AppState::db()` opens a synchronous rusqlite connection and `Database::open` re-runs the full `init_schema()` migration check on every call — genuinely blocking work. A July 2026 full-server-hang incident (all HTTP, including static routes with no DB dependency, stopped responding until restart) traced to exactly the class of bug the Gotchas section below already warned about in principle: `skills.rs`'s `api_skills` / `api_skill_detail` / `api_skill_files` / `api_skill_file` and ALL FOUR of `telemetry.rs`'s handlers ran their DB work directly on the tokio worker thread, unlike every other handler in this server. `api_skill_detail` is the worst offender on its own — `Database::skill_router_stats` scans the full `router_events` table and then runs one `router_session_adoptions` COUNT query PER `(skill, session)` pair found chosen, so on a busy install it's thousands of synchronous SQLite round trips in a single call — but `telemetry.rs`'s four handlers are hit far more often in practice: `api_summary`/`api_events`/`api_timeline` are polled every 5s by every open Overview tab, and the model-usage panel on top of that pages `/api/events` in a loop up to 10,000 rows (~20 sequential requests per poll tick). Enough concurrent viewers on either tab could tie up every tokio worker thread in sync SQLite work, at which point unrelated requests (including `/app.js`) have no free worker to run on. Both files are now fully wrapped; if you add a new handler to either file (or anywhere else touching `db`/filesystem), wrap its body in `spawn_blocking` from the start — do not rely on "it's a small query" as a reason to skip it, since the whole point of this incident is that per-request cost is not visible from the handler's own code, only from the request volume hitting it.
- **`stats_cache.rs` caches the two non-owner-scoped radar aggregates for 45s, keyed by `db_path`.** `api_skill_detail` folds `Database::skill_router_stats(since_ts)` and `Database::skill_feedback_counts_all()` into the radar/`radar_avg`/`feedback_stats` computation; both scan the WHOLE `router_events`/`skill_feedback` tables with no owner filter (the router blends feedback/usage regardless of which pool produced it — see `db/AGENTS.md`), so they're safe to share across every viewer of every skill. `stats_cache::router_and_feedback_stats(db, db_path, since_ts)` is the only correct way to get them inside `api_skill_detail` — do not call `db.skill_router_stats`/`db.skill_feedback_counts_all` directly there. The caller's owner-scoped pieces (`compare_resources`, `max_usage`, `radar_avg`'s corpus loop) stay computed fresh per request — they're in-memory folds over maps this cache already returns, not additional DB scans, and a non-admin's average must never touch another user's private counts, so they can't be cached behind a scope-blind key. Accepted tradeoff: a feedback vote can lag up to 45s before it moves the radar for OTHER viewers polling the same skill — documented in `stats_cache.rs`'s module doc, not a bug.

## Cross-module dependencies
- `crate::core::db::{Database, RouterEvent, User}` — every handler opens its own `Database` per request (`!Sync` rusqlite `Connection`); `AppState` carries only the db path.
- `crate::core::manager::SkillManager` — skill resolution, install, usage recording.
- `crate::core::market` (as `mkt`) — source list, cache, fetch, `install_single`, `find_skill_in_sources`, `is_root_skill_payload`.
- `crate::core::recommend` — `recommend_for_user_with_client`, `recommend_for_user`, `reevaluate_skill`, `RecommendConfig`/`Provider`/`SessionMode`/`ProviderEntry`, `format_for_hook_full`, `local_ipv4`.
- `crate::core::auth` (as `authmod`) — bearer/cookie parsing, password + api_key hashing, session cookie builders.
- `crate::core::prefs::UserPrefs`, `crate::core::paths::AppPaths`, `crate::core::cli_target::CliTarget`, `crate::core::resource::ResourceKind`.
- `axum-server` with `tls-rustls` — pure-Rust TLS termination for `bind_rustls`. The `rustls` feature is the conscious choice over native-tls so the single-static-binary invariant survives across OS targets (no openssl runtime dep, no system trust-store coupling).
- `rustls-pemfile` — parses PEM cert chains in `tls::leaf_fingerprint_sha256` so the fingerprint endpoint doesn't have to re-implement RFC 7468 boundary detection.
- `dashmap` — lock-free concurrent map backing `middleware::rate_limit`'s buckets.

## Gotchas / where bodies are buried
- **Every blocking handler hops `tokio::task::spawn_blocking`** because rusqlite + `reqwest::blocking` are sync; the market preview/install/refresh handlers additionally build a nested `tokio::runtime::Runtime` inside the blocking closure to drive async reqwest. This double-runtime is legal and intentional — do not "simplify" it across the async boundary. This was a stated rule, not just an aspiration, until the 2026-07 audit found `skills.rs` and `telemetry.rs` violating it (see the invariant above) — treat any new handler that reads `db` or touches the filesystem without a `spawn_blocking` wrapper as a bug, not a style nit.
- **Known remaining minor gaps from the 2026-07 audit, left as-is (documented, not a TODO list to silently "clean up")**: `recommend.rs::handle_feedback` opens `state.db()` and calls `require_user` BEFORE hopping to `spawn_blocking` (every other handler in this server does the auth check INSIDE the closure) — a single indexed lookup, not a scan, so the exposure is small, but it's an inconsistency if you're touching that function anyway. `market.rs::refresh_all_sources` calls `mkt::save_cache` (a sync file write) inside a bare `tokio::spawn(async move { .. })`, not `spawn_blocking` — low blast radius (a handful of small JSON writes, only on an explicit `/api/market/refresh` call, never polled) but the same class of issue. Neither caused the July incident (that was `skills.rs` + `telemetry.rs`, the two files actually polled every 5s); fix them if you're already in the area, don't go out of your way for them.
- **`api_market_preview` races multiple mirror URLs** via `tokio::task::JoinSet` (raw.githubusercontent / ghfast.top / jsdelivr / jsdmirror), first 200 wins, siblings aborted. `api_market_preview_files` walks the jsdelivr tree in-memory (nested `find_dir` fn) then falls back to the GitHub Contents API (honors `GITHUB_TOKEN`). Both cache to `~/.runai/market-cache/preview-{md,files}/` with 1h success / 5min failure TTL.
- **`EventJson` is defined in `telemetry.rs` but used by `skills.rs`** (`SkillDetailResponse.events`) — it's `pub(super)` for that reason.
- **DTO structs are `pub(super)`**, not private: route handlers are `pub(super)` (visible to `app.rs`'s router), so their request/response types must be at least as visible or Rust rejects the "private type in public interface".
