# server — LLM module guide

> This folder (`src/server/`). One-liner: axum HTTP dashboard + remote-hook + multi-user API, one file per route family.

## Public surface (stable — external code depends on these paths)
The entire crate-visible surface is exactly four items, re-exported from `mod.rs`. Everything else is `pub(super)` (module-internal) — there is no other public API.
- `crate::server::serve(host: &str, port: u16) -> Result<()>` — async entrypoint with default owner mode + no TLS. Used by `ensure_running`'s detached spawn so the auto-spawned dashboard stays single-user. Otherwise prefer `serve_with`.
- `crate::server::serve_with(host, port, mode: ServerMode, tls_cert: Option<PathBuf>, tls_key: Option<PathBuf>) -> Result<()>` — canonical entrypoint that runs `server_mode::validate_startup` first (only rejects a half TLS config — exactly one of cert/key; TLS is otherwise opt-in, no forced HTTPS) and stamps `mode` / TLS material onto `AppState`. Warns on stderr when an exposed bind runs cleartext. Called from `cli::dispatch` for `runai server`.
- `crate::server::ensure_running(host: &str, port: u16) -> Result<EnsureStatus>` — idempotent "is the runai dashboard up, if not spawn it detached" helper. Called from the TUI auto-spawn path and `cli::dispatch`; readiness is a runai-specific `GET /` probe requiring the `runai-dashboard: 1` response header, not a raw TCP port check.
- `crate::server::EnsureStatus` — `{ AlreadyRunning, Started }` enum returned by `ensure_running`.

Consumers: only `src/cli/dispatch.rs` (5 call sites). The split preserved every path — zero consumer edits.

## Invariants (load-bearing — do not break silently)
- **Remote HTTP MCP is a SEPARATE surface from the stdio `sm_*` tools** (`mcp_http.rs`, PLANNING §1.6). `src/mcp/tools` is the local 21-tool stdio MCP that manages the box running runai; `mcp_http.rs` is the remote, team-user, HTTP (rmcp streamable-HTTP) MCP at `/mcp`. The two are independent — do not merge their tool sets or share the `SmServer` type. The transport is configured **stateless + JSON-response** (`StreamableHttpServerConfig::default().with_stateful_mode(false).with_json_response(true)`) so every POST is answered with one `application/json` JSON-RPC envelope (no session header, no SSE framing). Auth is enforced by `mcp_auth_gate` **in front of** the transport: it resolves the user via `state::current_user` (Bearer header or `runai_session` cookie), returns `401 + empty body` on failure (uniform with §2.3 item 4/5), and on success inserts `OwnerId(user_id)` into the request extensions. The streamable-HTTP transport copies the full `http::request::Parts` (incl. `.extensions`) into each tool's `rmcp::service::RequestContext`, so tool bodies read the owner via the `Extension<axum::http::request::Parts>` extractor then `parts.extensions.get::<OwnerId>()` — never re-parse credentials inside a tool. New remote tools that touch per-user resources MUST scope through this `OwnerId` and the owner-aware `db` queries (`list_resources_for_user` / `find_resource_by_name_for_user`), never the public-pool-only `SkillManager::list_resources`. The `/mcp` sub-router is `.merge()`d into the main router with its own `from_fn_with_state` auth layer so the gate covers `/mcp` and nothing else.
- **Server startup uses the same env-aware data-dir resolver as CLI/MCP.** `app.rs::serve_with` calls `AppPaths::try_default_path()` before building `AppState`, so `RUNE_DATA_DIR` / `SKILL_MANAGER_DATA_DIR` affect the dashboard, `/recommend`, and remote MCP exactly like ordinary CLI commands. Legacy migration failures propagate and abort startup; do not replace this with `default_path()` or a fresh `SkillManager::new()` when the handler already has `state.db_path`.
- **`ensure_running` must not treat any open port as a dashboard.** The helper probes `GET /` and requires the server-owned `runai-dashboard: 1` response header before returning `AlreadyRunning` or `Started`; a different service on the requested port must surface as a readiness failure. This protects SessionStart hooks and the TUI auto-spawn path from claiming the dashboard is available when the port is occupied by something else, without coupling readiness to UI title/body text. `tests/server_ensure_cli_e2e.rs` covers both an existing runai server and a dummy non-runai HTTP listener.

  **A blocking install inside an MCP tool MUST run on a std thread, never directly.** The rmcp tool fns run on tokio async worker threads. `mcp_http.rs::market_install` calls `install_github_repo_filtered_for` / `Market::install_single` which do `Runtime::new().block_on(...)` internally — calling `block_on` from within a runtime PANICS ("Cannot start a runtime from within a runtime"), the worker dies, and the MCP call HANGS forever (2026-06-08: market_install hung for minutes; the dashboard's `api_market_install` avoids this because it's wrapped in `spawn_blocking`). The tool wraps the blocking closure in `tokio::task::block_in_place(|| std::thread::scope(|s| s.spawn(work).join()))` — the std thread has no ambient runtime so the nested runtime is legal, and `scope` lets `work` borrow `self`/`parts`. Any new MCP tool that hits an install/`block_on` path must do the same. (`community_install`/`public_install` are pure `copy_dir_recursive`, no runtime, so they don't need it.) The GitHub HTTP clients (`market::fetch`/`download`/`install`, `installer`) also carry a 30-60s `.timeout(...)` — a stalled connection on a timeout-less client is the other way install hangs.
  **Remote MCP tools are role-based exactly like the market HTTP handlers** (§1.6). Each tool body calls `RemoteMcpServer::caller(&parts)` which reads `OwnerId` from the extensions and re-resolves it to the full `User` via `db.find_user_by_id` (the gate only stamps the uid; tools need `is_admin`). Role branch is identical to `market.rs`: an ADMIN manages the PUBLIC pool (`library_list` = public pool, `market_install` owner=`None` → `skills_dir()`, `skill_get`/`skill_bundle` scope `"*"`), a regular user manages their own PRIVATE pool (`library_list` = `owner_user_id == uid`, `market_install`/`community_install`/`public_install`/`skill_upload` owner=`Some(uid)` → `user_skills_dir(uid)` after `ensure_user_dirs`). Tools do NOT re-implement business logic — they proxy the same primitives the HTTP handlers use (`mkt::find_skill_in_sources` + `install_github_repo_filtered_for`/`register_local_skill_for`, `db.get_community_skill` + `copy_dir_recursive`, `db.create_promotion`, the gz-tar walk). `public_install` is regular-user-only (an admin already owns the public pool). Tool errors surface in the `result` string prefixed `"error: "` (the uniform `Json<TextResult>` shape), not as a JSON-RPC transport error, so a client always gets a structured answer. `skill_bundle` returns the gz tar base64-encoded (JSON-safe); `skill_upload` takes per-file base64 content and rejects unsafe relative paths before creating any parent directories, so a traversal entry cannot leave orphan directories outside the target skill dir before failing.
  **Acquisition into a user's private pool is no-overwrite by default.** `api_community_install`, MCP `community_install`, MCP `public_install`, MCP `skill_upload`, and the regular-user branches of `market_install`/`api_market_install` call `paths::refuse_existing_path` before copy/download/write. Existing real directories and dangling symlinks both reject with a user-facing error and the old payload stays untouched. There is no implicit "fresh copy replaces mine" behavior; adding replacement later requires an explicit `force`/`replace` parameter and a separate destructive-path e2e.
  **Failed acquisition rollback is shared and non-silent.** Any server/MCP path that creates `<data>/skills/<name>` or `<data>/users/<uid>/skills/<name>` before the DB row exists must call `state::rollback_created_skill_dir(root, dest, context)` on copy/download/write/register failure. The helper only removes one direct real directory child of the expected pool root, rejects symlinks/nested/escaped paths, and propagates cleanup failure together with the original error. Never go back to `let _ = std::fs::remove_dir_all(...)` in install/upload handlers: a swallowed cleanup error leaves an orphan payload that blocks future installs while the API reports only the first failure.
- **Skill-name validation is one policy across server surfaces.** Any endpoint/tool that will later resolve a skill through `/skills/*`, copy it into `<data>/skills/<name>`, `<data>/users/<uid>/skills/<name>`, or `<data>/community/<uid>/<name>` must use `core::paths::is_safe_skill_name` before DB writes or filesystem joins. Do not broaden one surface independently (for example allowing `.` in community/MCP names): it creates rows/payloads that upload successfully but cannot be consumed by the canonical skill routes.
- **Community re-upload is restore-on-failure, not delete-then-write.** `api_community_upload` allows the same uploader to replace the same skill name, but it must first prove the payload is one direct real child of `<data>/community/<uid>/`, move the previous payload to a sibling `.runai-replace-*` backup, move the new payload into place, then write `community_skills`. If the DB upsert fails, restore the backup and remove the new payload; if the DB succeeds, remove the backup through the same direct-child rollback helper. Never reintroduce a bare `remove_dir_all(final_dir)` here: it can leave a community row pointing at missing/new-but-unindexed bytes after a mid-flight failure.
- **Community delete is staged until the DB row is gone.** `api_community_delete` must validate the payload as one direct real child of `<data>/community/<uid>/`, rename it to a sibling `.runai-delete-*` staging dir, delete the `community_skills` row, then purge the staging dir through `rollback_created_skill_dir`. If the DB delete fails, rename the staging dir back before returning 500. A failed delete must leave either both row and payload present or neither present; never delete the row first and leave an unindexed payload.
- **Admin user delete stages physical dirs before the DB cascade.** `api_admin_users_delete` must validate `<data>/users/<uid>` and `<data>/community/<uid>` as direct real children, rename each existing dir into a sibling `.runai-delete-user-*` staging dir, then run the DB cascade transaction. If staging or DB work fails, restore every staged dir before returning an error; after commit, purge staging through the direct-child rollback helper. Do not make this best-effort cleanup after deleting rows: a 200 response with orphaned private/community payloads leaves user skill bytes invisible and unrecoverable.
- **`mod.rs` holds the `include_str!` consts at `../../`** (`src/server/mod.rs` is one dir deeper than the old `src/server.rs`, so `../web/...` → `../../web/...`, `../scripts/...` → `../../scripts/...`). Five `CLIENT_*` consts feed `install.rs`; `INDEX_HTML`/`APP_JS`/`APP_CSS` feed `app.rs`.
- **Path-traversal guards moved verbatim.** `skills.rs::api_skill_file` and `handle_skill_file` both `canonicalize()` the skill_dir root and the joined target then assert `target_real.starts_with(&root_real)` before reading. Never relocate the canonicalize/`starts_with` check away from the handler that joins the user-controlled `?path=` / `{*path}`.
- **`serve_index` cache-bust string-replace** rewrites the literals `"/app.css"` and `"/app.js"` to append `?v=<BUILD_ID>`. If web assets are ever split into `/css/*` / `/js/*`, this replace MUST be extended to each new URL (see `docs/decoupling/PLAN.md` §6c) — there is no compile gate for a stale-cache bug.
- **Shared private helpers live in exactly one home.** `state.rs` owns `current_user`/`require_user`/`current_owner_id`/`resolve_skill_dir`/`require_admin`/`resolve_view_user` + `AppState::public_server_url`; siblings import via `use super::state::X`. `error.rs` owns `ApiError`. `market.rs` owns `spawn_enrich` + `InstallResp` (used by `market_github.rs` + `mcp_http.rs`). Keep them `pub(super)`, never `pub` — widening leaks the API.
- **`spawn_enrich` must stay observable.** It runs `recommend enrich --name …` in a detached thread that WAITS on the child (`cmd.output()`) and logs its full stdout/stderr via `tracing` (→ the server log). It must NEVER go back to piping the child to `/dev/null` — that left freshly-installed skills stuck 待富集 with zero trace, undebuggable (2026-06-08). Every install/upload path that adds a skill calls it: `market.rs` (market install), `market_github.rs` (paste-a-repo), `mcp_http.rs` (`market_install`/`public_install`/`community_install`/**`skill_upload`** — the upload path was missing it, so uploaded skills also stayed 待富集). The install handlers also `tracing::info!` the install itself.
- **Per-user prefs round-trip is generic top-level merge** (`prefs.rs::merge_prefs_patch`). `recommend_scope` (PLANNING §1.6, the tri-state `my`/`public`/`both` that replaced `allow_public_recommend`) is just another top-level key — a partial `POST /api/prefs` with only `{"recommend_scope":"my"}` flips it without touching siblings, and the merged blob round-trips through `UserPrefs::from_json_str` to the right enum. `SettingsView`/`SettingsPatch` (the admin global `RecommendConfig`) deliberately carry NO scope field — scope is per-user prefs, never global settings. Do NOT reintroduce `allow_public_recommend` anywhere in the server DTOs.
- **Market install + query are role-based (PLANNING §1.6).** `market.rs::api_market_install`, `market_github.rs::api_install_github`, and the `in_my_library` field in `api_market_list` / `api_parse_github` all branch on `user.is_admin`. Admin manages the PUBLIC pool: install owner = `None` (writes to `skills_dir()` with `owner_user_id IS NULL`, NO `ensure_user_dirs`), and `in_my_library == installed` (the public-pool set). Regular user manages their PRIVATE "我的库": install owner = `Some(uid)` (writes to `user_skills_dir(uid)`, `ensure_user_dirs` first), and `in_my_library` = skills in their own private pool (`owner_user_id == uid`). Market/GitHub install responses use `market::market_install_library_size(db, user)`: regular user → private-skill count, admin → `0` because the install landed in the public pool even if that admin account already owns legacy private rows. Count failures must propagate as handler errors rather than rendering `0`. Community install still uses `market::private_skill_count(db, uid)` because it always copies into the caller's private pool. The deprecated `user_skill_library` subscription table is NOT touched by these handlers anymore (`library_add` / `library_count` calls removed); do NOT reintroduce them — "我的库" == private skills. These helpers are `pub(super)` in `market.rs` and shared with `market_github.rs` / `community.rs`.
- **`user_skill_library` is public-import state only.** `library.rs` is the only HTTP route family that mutates it directly: `add` first verifies every requested name resolves via `find_resource_by_name_for_user(Skill, name, None)` before writing any row, so mixed valid+invalid batches are atomic; `fill` sources names from `top_public_skills`; `import-from-usage` ignores chosen skill names that are private or missing. Community/market/GitHub installs write private resources for regular users and MUST NOT call `db.library_add`. Admin/user counts that read imported public skills rely on this table staying public-only.
- **Community upload enrichment is owner-scoped.** `community.rs::require_enriched_skill` first verifies the resource row is the caller's own private skill, then checks `db.skill_ai_summary_for(name, Some(owner_uid))`. Do NOT call the legacy `skill_ai_summary(name)` wrapper here: it reads the public-pool summary only, so a correctly enriched private skill would be rejected as "not enriched". `tests/community_cli_e2e.rs::local_runai_community_cli_upload_list_install_delete_roundtrip` seeds only the owner's private summary and catches this regression through the real CLI upload path.
- **Remote feedback is owner-scoped end-to-end.** `recommend.rs::handle_feedback` first resolves the target with `find_resource_by_name_for_user` under `Some(caller_uid)` (regular) or `Some("*")` (admin), then calls `recommend::reevaluate_skill_in_scope` with the same scope. Do NOT call global `reevaluate_skill` from `/feedback`: same-name public/private rows make the permission pre-check and the actual write target diverge. `tests/feedback_scope_e2e.rs` covers both the same-name private shadow case and cross-user private rejection with no LLM call.
- **Admin 用户库 view is strictly-private + owner-joined** (`admin.rs::api_admin_user_library`, PLANNING §1.6). It MUST go through `db.list_private_skills_with_owner()` (INNER JOIN `resources` where `owner_user_id IS NOT NULL` with `users`), NOT `list_resources_for_user(_, Some("*"))` — the latter unions the public pool, which is the wrong set for "whose private skill is this". Enabled = `Linker::is_symlink` across `CliTarget::ALL` skill dirs (private skills normally aren't symlinked, so usually false — surfaced for parity); enriched = non-empty owner-aware summary row from `skill_ai_summary_all_owner_aware`.
- **Admin user count fields are authoritative.** `api_admin_users_list` / `api_admin_users_update` must propagate failures while computing `private_count`, `imported_public_count`, and `event_count`. Do not default count query failures to 0; that makes a corrupt DB look like an empty user library.
- **Skill list/detail enrich lifecycle is owner-aware.** `resources.enrich_in_flight/enrich_started_at/enrich_last_error` are written by resource id, so `skills.rs` must read them with `skill_enrich_status_all_owner_aware()` and look up `(name, owner_user_id)`. A name-keyed status map makes a same-name public failure appear on the private row or hides the private failure behind the public row.
- **Enrich metadata query failures are HTTP errors, not empty metadata.** `/api/skills`, `/api/skill/{name}`, and `/api/admin/user-library` must propagate failures from `skill_ai_summary_for`, `skill_llm_score_for`, `skill_ai_summary_all_owner_aware`, `skill_llm_scores_all_owner_aware`, and `skill_enrich_status_all_owner_aware` as 500. Do not use `unwrap_or_default()` there; a corrupt `resource_ai_summary`/`resources` table must not render every skill as unenriched or unscored.
- **Settings config load failures are HTTP errors.** `/api/settings` and every provider/settings mutation must propagate `RecommendConfig::load` errors. A missing file may render defaults, but an unreadable or unparsable existing `config.toml` must not render as default Settings or be overwritten by a later save.
- **Public-library promotion is owner-gated on submit, move-before-stamp on approve** (`promotions.rs`, PLANNING §1.6 Route A). `api_promote_submit` MUST verify via `find_resource_by_name_for_user(Skill, name, Some(uid))` that the row's `owner_user_id == uid` before `create_promotion` — submitting a public skill or another user's private skill returns 400, never silently enqueues. `api_admin_promotions_decide`'s `approve` branch runs `SkillManager::promote_skill_to_public(name, user_id)` FIRST and only calls `set_promotion_status(_, _, Approved)` if the physical move succeeds; a failed move (e.g. an existing public skill of that name) leaves the request `pending` and surfaces the error. Do NOT stamp `approved` before the move — that would mark a promotion done while the bytes never left the user pool. Both admin routes go through `require_admin`; the submit route through `require_user`.
- **Tenant isolation rules** (`resolve_view_user` / `current_owner_id` / `resolve_skill_dir`): telemetry, settings, and skill browse require auth even before first-user registration; bootstrap goes through `/users/register`. Non-admin is forced to own scope, admin is global-by-default, and private rows shadow public for the owner. `/api/event/{id}` returns 404 (not 403) on cross-tenant to block id enumeration.
- **Telemetry chosen-skill JSON parse failures are visible.** `telemetry.rs::EventJson::try_from` validates `router_events.chosen_skills_json` through the DB parser. `/api/events`, `/api/event/{id}`, and skill detail event lists must return 500 on corrupt JSON instead of rendering `chosen: []`; `/api/summary` and `/api/timeline` count hits only when the JSON is valid and non-empty. `api_library_import_from_usage` uses the same parser and surfaces corruption instead of silently skipping entries.
- **Detail payload reads are non-silent.** `api_skill_detail` and `api_community_skill_detail` read the backing `SKILL.md` as the primary detail content. A DB row whose payload file is missing or unreadable must return 500 with read context, not `200` with an empty `skill_md_content` / `readme`; otherwise disk corruption looks like an intentionally empty skill.
- **Community upload staging reads are non-silent.** `community.rs::find_skill_root` returns `Result<Option<PathBuf>>`: unreadable extracted directories/entries propagate with context, while only a fully readable tree with no `SKILL.md` becomes `uploaded archive does not contain SKILL.md`. Do not collapse `read_dir` failures with `.ok()` / `.flatten()` during payload normalization.
- **Admin 用户库 drill-in is owner-scoped via `?user_id=`** (PLANNING §1.6, 2026-06-08). The skill list/detail/files/file endpoints resolve their owner scope through `state::resolve_skill_view_scope(headers, db, ?user_id)`: an admin with `?user_id=<uid>` gets `Some(uid)` (so `find_resource_by_name_for_user` returns THAT user's private skill, shadowing a same-name public one — this is how admin reads a user's private SKILL.md content); admin with no target gets `Some("*")`; a non-admin is pinned to self and any other `?user_id` → 403. Content resolution for files goes through `resolve_skill_dir_scoped` with that scope, NOT the caller-derived `resolve_skill_dir`. Do NOT let a non-admin pass `?user_id` to read another user's private skill — the scope resolver is the single gate.
- **`/skills/get` and remote MCP `skill_get` adoption counting use the resolved row id.** `state::resolve_skill_dir[_scoped]` returns `ResolvedSkillDir { dir, resource_id }`; `resource_id` is `Some(id)` when the DB row resolved (public or private) and `None` only for the public on-disk compatibility fallback. `skills.rs::handle_skill_get` and `mcp_http.rs::skill_get` must bump `db.record_usage(resource_id_or_row_id)` before returning success when a DB row is present. Do not re-look-up by name or ignore those DB writes: same-name private/public rows make name-only counting wrong, and swallowed write errors make router telemetry lie.
- **Server mode gates the register/install surface** (PLANNING §1.1 + §1.2). `state.mode` is the source of truth. `auth.rs::api_register` returns 403 when `state.mode == ServerMode::Owner`. `install.rs::handle_install_script` / `handle_install_ps1` / `handle_uninstall_script` / `handle_uninstall_ps1` all return 404 (empty body) when owner mode — single-user self-serve has no remote client surface. In team mode they call `render_install_script(template, mode, server_url)` which (a) strips every `# === RUNAI_SECTION:<other>-only START === ... END ===` block (marker grammar is line-based and identical for `.sh` + `.ps1` because both use `#` line comments), (b) drops the START/END marker lines for the requested mode too so the served file is clean, (c) replaces `{SERVER_URL}` with `AppState::public_server_url`, preserving `https://` when TLS is configured and substituting LAN IPv4 for loopback Host headers. Both client install scripts (`scripts/runai-client-install.sh` + `.ps1`) wrap their team-flow content in `# === RUNAI_SECTION:team-only ... ===` and reserve an empty `# === RUNAI_SECTION:owner-only ... ===` scaffold for symmetry. Do NOT re-derive the mode from "are there users registered?" — that's exactly the implicit recovery model the flag replaces.
- **TLS bind path (PLANNING §2.3 item 2, relaxed)**: TLS is fully opt-in for every mode — there is no forced-HTTPS guard. `serve_with` runs `server_mode::validate_startup(mode, host, tls_cert, tls_key)` before binding, which now only rejects a *half* TLS config (exactly one of cert/key — an operator typo). team + non-loopback + no TLS is allowed and serves plain HTTP; `serve_with` prints a stderr warning that api_key + prompt traffic is unencrypted. When both `tls_cert` AND `tls_key` are present (any mode), the bind switches from `axum::serve(TcpListener)` to `axum_server::bind_rustls(addr, cfg)` — the rustls cert + key are loaded via `tls::load_rustls_config`. Both code paths attach `into_make_service_with_connect_info::<SocketAddr>()` so the rate-limit middleware sees the peer IP. (Relaxed on the maintainer's call: the self-signed bootstrap — client needs the CA before the first HTTPS fetch, and the hook's fingerprint pre-check couldn't complete a self-signed handshake without `--cacert` — broke LAN self-use harder than the cleartext-sniff threat justified.)
- **Anti-explore + uniform 404 (PLANNING §2.3 item 4)**: `app.rs::empty_404` is wired as the global fallback (`.fallback(empty_404)`) AND explicitly mounted on every known self-describing-API probe path (`/openapi.json` / `/openapi.yaml` / `/swagger` / `/swagger.json` / `/swagger-ui*` / `/docs*` / `/api-docs*` / `/__schema` / `/graphql` / `/redoc`) via `any(empty_404)` so HEAD/POST/OPTIONS probes return the same `404 + empty body` as GET. Do NOT add diagnostic JSON, `Content-Type`, or `X-*` headers to `empty_404` — the contract is "every miss is bytewise the same response so an attacker cannot distinguish unknown-path from auth-required from internal-error".
- **TLS fingerprint endpoint (PLANNING §2.3 item 3)**: `GET /api/tls/fingerprint` returns `{"fingerprint":"<64-char lowercase hex>"}` (SHA-256 of leaf cert DER) when `AppState.tls_cert` is set, else `404 + empty`. Unauthenticated by design: an attacker on the wire already sees the cert on TLS handshake, exposing the fingerprint over HTTP adds no info. Both client install scripts write this to `~/.runai-server.json` / `%USERPROFILE%\.runai-server.json` at install time. The hook wrappers re-fetch it on every prompt and refuse to forward if the live value diverges from the pinned one; the bash and PowerShell companion CLIs do the same before any HTTPS API request. **Self-signed cert handling**: the runai team cert is self-signed, so every client-side request to the server passes `--insecure` (bash) / `-SkipCertificateCheck` (PS7) / `ServerCertificateValidationCallback` (PS5.1) — the fingerprint pin, not CA-chain validation, is the MITM gate. `--insecure` only skips the chain step a self-signed cert can never satisfy; an attacker still needs the server's private key to present a cert whose fingerprint matches the pin. The bash client gates `-k` on `scheme == https` via a scalar `CURL_TLS` var (scalar not array because macOS bash 3.2 errors on an empty array under `set -u`).
- **Rate-limited sub-routers (PLANNING §2.3 item 6)**: `/auth/login`, `/api/community/upload`, `/skills/get/{name}` each live in their own `Router::new().route(...).layer(middleware::from_fn(...))` sub-router that is `.merge()`d into the main router. Mounting via sub-router (not `.layer` on the main router) confines the limit to that path family — no risk an unrelated handler gets throttled by accident. Over-quota responses are produced by `rate_limit_layer` ahead of the handler, so even malformed requests count toward the bucket.
- **Remote hook activation must carry runtime Bearer.** `/recommend` receives Bearer from the installed hook wrapper; the hook output it returns must not print that secret. Instead it renders Bash that reads `~/.runai-identity` at execution time and sends `Authorization: Bearer ...` to `/skills/get`, `/skills/file`, and `/feedback`. `/skills/get` must use the same runtime-auth pattern in its sibling-file appendix; otherwise private skill references/scripts fall back to anonymous/public resolution.
- **Login failure is uniform (PLANNING §2.3 item 5)**: `auth.rs::api_login` returns `Response` (not `Result<Json<>, ApiError>`) and routes all three failure modes (`find_user_by_username = None`, `user.disabled`, `verify_password = false`) through `login_failure()` which produces `401 + {"error":"invalid_credentials"}`. Do NOT introduce a "user not found" vs "wrong password" distinction in the wire response — log it server-side if you need to, but the body must stay the canonical `LOGIN_FAILURE_BODY` constant so an attacker cannot enumerate accounts via response diffing.
- **Registration establishes a session**: `auth.rs::api_register` returns `Response` and sets the `runai_session` cookie (same builder as login) on success, so a brand-new dashboard user is authenticated immediately instead of having to log in again. The frontend pairs with this: `loadSkills` (and the other per-user loaders) go through the `api()` wrapper which also sends `Authorization: Bearer` from the localStorage api_key — so a cookie-less-but-key-present session still authenticates. A raw cookie-only `fetch('/api/skills')` would 401 right after registration and render an empty library on first run (regression caught by `tests/browser/newuser.spec.cjs`).
- **No anonymous private reads before first registration**: `state::private_data_locked(db)` returns `true` unconditionally. `resolve_view_user` (used by `api_summary` / `api_events` / `api_timeline` / `api_event_by_id`) and the inline check in `api_skills` / `api_skill_detail` both consult it, so telemetry, settings, and skill browse return 401 until the first user registers and sends Bearer/cookie auth. Static dashboard assets and `/install` stay public so a teammate can reach the registration flow.
- **Provider testing is a model request, not a URL ping.** `prefs.rs::api_test_provider` is admin-gated, loads the saved provider by id, then calls `recommend::test_provider_request`. Success means the configured provider/model/key answered a tiny LLM prompt through the selected transport. Transport/API failures return `200 + {ok:false,error}` so the Admin pane can show the model failure inline instead of treating it as a broken dashboard endpoint.

## Cross-module dependencies
- `crate::core::db::{Database, RouterEvent, User}` — every handler opens its own `Database` per request (`!Sync` rusqlite `Connection`); `AppState` carries only the db path.
- `crate::core::manager::SkillManager` — skill resolution, install, usage recording.
- `crate::core::market` (as `mkt`) — source list, cache, fetch, `install_single`, `find_skill_in_sources`, `is_root_skill_payload`.
- `crate::core::recommend` — `recommend_for_user`, `reevaluate_skill`, `RecommendConfig`/`Provider`/`SessionMode`/`ProviderEntry`, `format_for_hook_full`, `local_ipv4`.
- `rmcp` with `transport-streamable-http-server` — backs `mcp_http.rs`'s `/mcp` endpoint (`StreamableHttpService` + `LocalSessionManager`). The feature pulls in the tower `Service` impl that nests into axum via `any_service`. Tool argument/return structs derive `rmcp::schemars::JsonSchema` (schemars is NOT a direct workspace dep — always go through `rmcp::schemars`).
- `crate::core::auth` (as `authmod`) — bearer/cookie parsing, password + api_key hashing, session cookie builders.
- `crate::core::prefs::UserPrefs`, `crate::core::paths::AppPaths`, `crate::core::cli_target::CliTarget`, `crate::core::resource::ResourceKind`.
- `axum-server` with `tls-rustls` — pure-Rust TLS termination for `bind_rustls`. The `rustls` feature is the conscious choice over native-tls so the single-static-binary invariant survives across OS targets (no openssl runtime dep, no system trust-store coupling).
- `rustls-pemfile` — parses PEM cert chains in `tls::leaf_fingerprint_sha256` so the fingerprint endpoint doesn't have to re-implement RFC 7468 boundary detection.
- `dashmap` — lock-free concurrent map backing `middleware::rate_limit`'s buckets.
- `base64` — JSON-safe encoding for the remote-MCP `skill_bundle` (gz tar → base64) and decoding for `skill_upload` (per-file base64 content). Direct dep (added with the §1.6 remote MCP tool set).

## Gotchas / where bodies are buried
- **Every blocking handler hops `tokio::task::spawn_blocking`** because rusqlite + `reqwest::blocking` are sync; the market preview/install/refresh handlers additionally build a nested `tokio::runtime::Runtime` inside the blocking closure to drive async reqwest. This double-runtime is legal and intentional — do not "simplify" it across the async boundary.
- **`api_market_preview` races multiple mirror URLs** via `tokio::task::JoinSet` (raw.githubusercontent / ghfast.top / jsdelivr / jsdmirror), first 200 wins, siblings aborted. `api_market_preview_files` walks the jsdelivr tree in-memory (nested `find_dir` fn) then falls back to the GitHub Contents API (honors `GITHUB_TOKEN`). Both cache to `~/.runai/market-cache/preview-{md,files}/` with 1h success / 5min failure TTL. The preview-files cache key includes both `repo_path` and `skill_name`, because skills.sh aggregator rows can share an empty `repo_path`; an empty path must not make unrelated skills reuse one file listing. For root-skill repos, both jsdelivr and GitHub fallback require a top-level `SKILL.md` before accepting the repo root and filter entries through `core::market::is_root_skill_payload` (directory names are checked as `name/`) so README/license/CI metadata do not appear in the sibling-file preview.
- **`EventJson` is defined in `telemetry.rs` but used by `skills.rs`** (`SkillDetailResponse.events`) — it's `pub(super)` for that reason.
- **DTO structs are `pub(super)`**, not private: route handlers are `pub(super)` (visible to `app.rs`'s router), so their request/response types must be at least as visible or Rust rejects the "private type in public interface".
